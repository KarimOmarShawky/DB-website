Indexing

A. Exam Priority

Medium priority  Relevant ideas appear in 4 of 8 readable papers: 2013, 2019, 2021, 2021 SIS312. Each question is short (1–2.5 marks).

  • Primary index: sparse or dense — 1 paper (2021); Indexes on heap files must be dense — 1 paper (2021 SIS312); Primary vs secondary vs clustering index — 1 paper (2013).

  • MAX / MIN with a B-tree is taught in the Week 04 slides, so it is counted and answered in Lecture 3.

B. Short Revision

1. What an index is

  • An auxiliary file of entries ⟨field value, pointer⟩, always sorted on the indexing field, so it can be binary-searched. It is much smaller than the data file because its entries are small.
  • It speeds up searches (fields used in WHERE) but slows down insert, delete and update: a change in the data means a change in the index.
  • Data moves in blocks. Blocking factor bfr = block size / record size = records per block.
  • A file is either a heap (unordered) or sequential (ordered on some field).

Secondary indexes are less efficient than primary indexes: the matching records are scattered, so one search value can cost several data blocks (Question 1.5).

4. Composite index

CREATE INDEX idx_dept_sal ON EMPLOYEE (Dept_No, Salary); — entries are sorted by Dept_No first, then by Salary inside the same Dept_No. Leftmost-prefix rule: the index helps a condition on Dept_No, or on Dept_No and Salary, but not on Salary alone.

5. Multilevel index and B-tree

  • Multilevel index: when the index is too large for memory, build a sparse index on the index itself (second level) and repeat until the top level fits in one block. Faster search, slower updates.
  • B-tree: a multilevel index with a tree structure. Balanced — all leaves are at the same level. Each node is one disk block and holds n keys and n + 1 pointers. Usually three levels: root, intermediate, leaves.
  • Keys are in sorted order from left to right, which is why MIN is the left-most key and MAX the right-most (Lecture 3).
  • SQL: CREATE INDEX index-name ON relation-name (attribute-list); DROP INDEX index-name.
Common mistakes. A sparse index on a heap file (impossible) · saying a sparse index can prove a key is missing without reading data · “a primary index is always sparse” (usually, not always) · more than one primary index on a file · calling an index on an unordered non-key field a clustering index.

Question 1.1Past exam⚠ Repeated in 2 exam papersDense vs sparse, missing keys

Source: Past exam — 2019, Q2.3, PDF page 11 [2 marks]; 2021, Q1(b), PDF page 14 [1.5 marks]. (Exact wording. Neither paper has an answer key.)

Idea tested: Dense vs sparse index for non-existent keys

Appeared in: 2 verified exam papers — 2019, 2021.

Exact or similar repetitions: Exact repeat: the same sentence in both papers. Related dense/sparse questions with a different point: Question 1.2, Question 1.3 and Question 3.8.

Question:

“When the index fits in memory and most queries are searching for keys that do not exist in the relation, dense indexes are always better than sparse indexes? Why or why not?”

Model answer

Yes — for this workload the dense index is better.

  • A dense index has an entry for every key. If K is not in the index, it is not in the file: the miss is answered in memory with 0 disk accesses.
  • A sparse index only has the first key of each block. K can be missing from the index and still be in the file, so every miss costs one data-block read to check.
  • The usual advantage of a sparse index (smaller, fits in memory) does not count here because the question says the index fits in memory.

Example (slide 11 file, search 45): dense index 10, 20, …, 80 → 45 is not there → stop. Sparse index 10, 30, 50, 70 → entry 30 → read block [30, 40] → not found.

On “always”: true under the two stated conditions. If the dense index did not fit in memory, or the file had many inserts and deletes, the smaller, cheaper-to-maintain sparse index could win.

Basis: Week 02 — Indexing, W2&3&4.pdf, slide 13 (PDF page 13), row “Answers ‘does K exist?’”.

Question 1.2Past examTested in 1 exam paperPrimary index: sparse or dense

Source: Past exam — 2021, Q1(c), PDF page 14 [2.5 marks]. (Faithful paraphrase; the paper prints “True of False why and give example”. No answer key.)

Idea tested: Primary index: sparse or dense

Appeared in: 1 verified exam paper — 2021.

Exact or similar repetitions: Asked once. Related: Question 1.3 (heap files) and Question 1.4 (index types).

Question:

“Primary index can be sparse or dense index.” True or False? Why? Give an example.

Model answer

True.

  • A primary index is built on the ordering key of a sorted file. Because the file is sorted, one entry per block (the first key of the block) is enough, so it is usually sparse.
  • Nothing stops us from keeping one entry per record. That is a dense primary index: larger, but it can answer “does K exist?” without reading the data.

Example: sorted file with blocks [10, 20] [30, 40] [50, 60] [70, 80]. Sparse primary index: 10, 30, 50, 70 (4 entries). Dense primary index: 10, 20, 30, 40, 50, 60, 70, 80 (8 entries).

Contrast: a secondary index has no choice — it must be dense.

Basis: Week 02 — Indexing, W2&3&4.pdf, slides 11, 16, 26 (PDF pages 11, 16, 26) — “A primary index is usually sparse / Dense”.

Question 1.3Past examTested in 1 exam paperHeap files need dense indexes

Source: Past exam — 2021 SIS312, Q1(b), PDF page 17 [2 marks]. (Exact wording. Official key available.)

Idea tested: Indexes on heap files must be dense

Appeared in: 1 verified exam paper — 2021 SIS312.

Exact or similar repetitions: Asked once. It is the reverse side of Question 1.2: an ordered file allows a sparse index, an unordered file does not.

Question:

“Indexes on heap files must be dense” True or False? Why with example?

Model answer

True.

A sparse index stores only the first key of each block and relies on the order of the file: every key between two entries must be in the first entry’s block. A heap file is in insertion order, so the first key of a block says nothing about the other records in it. Every record therefore needs its own index entry — a dense index.

Example: heap blocks [20, 40] [10, 20] [50, 30]. A sparse index would hold 20 → block 1, 10 → block 2, 50 → block 3. Searching 40 or 30 fails: nothing tells us which block they are in. A dense (secondary) index lists 10, 20, 20, 30, 40, 50, each with its own pointer.

Official key: “True [1 mark]. As the file is not sorted so the block contains records not sorted [1 mark].”

Answer-key correction: the key is correct but incomplete — the question asks for an example and the key gives none. Add one as above.

Basis: Week 02 — Indexing, W2&3&4.pdf, slides 12–13, 21, 26 (PDF pages 12–13, 21, 26).

Source: Lecture slides — Week 02 — Indexing, W2&3&4.pdf, slides 22, 25 (PDF pages 22, 25). Adapted from a lecture slide example.

Idea tested: Secondary index on a non-key field

Appeared in: 0 verified exam papers.

Exact or similar repetitions: No exam question uses this figure. It explains why the cost of a secondary index on a non-key is x + 1 + s (Lecture 5).

Question:

A secondary index on a non-key field K has the entries 10, 10, 20, 20, 20, 30, 40, 50, 50, 60. The data file is not ordered on K and stores two records per block:

B1 [20, 40]   B2 [10, 20]   B3 [50, 30]   B4 [10, 50]   B5 [60, 20]

How many data blocks are needed to retrieve all the tuples with search key = 20? What does this show about secondary indexes?

Model answer

3 data blocks: B1, B2 and B5.

The three index entries for 20 point into three different blocks, so each matching record costs its own block read. If the file were ordered on K (clustering index), the three records would be adjacent and fit in two blocks.

Conclusion: on a non-key field a secondary index needs about one block access per matching record, so it is less efficient than a primary or clustering index.

Question:

CREATE INDEX idx_dept_sal ON EMPLOYEE (Dept_No, Salary);

The index entries are (1, 48,000) (1, 60,000) (3, 35,000) (3, 41,000) (3, 55,000) (5, 38,000) (5, 45,000) (5, 52,000). For each condition, say whether the index can locate the rows directly, and why.

  1. WHERE Dept_No = 5
  2. WHERE Dept_No = 5 AND Salary > 40000
  3. WHERE Salary > 40000
Model answer
  1. Yes. Entries are sorted on Dept_No first, so all entries with 5 are contiguous.
  2. Yes. Jump to Dept_No = 5, then read the contiguous entries with Salary > 40,000: (5, 45,000) and (5, 52,000) — only 2 records are fetched.

B. Short Revision

1. Steps of query processing ⚠ 2 papers

Query in a high-level language → ① Scanning, parsing, validating → intermediate form → ② Query optimizer → execution plan → ③ Query code generator → code → ④ Runtime database processor → result of query

  • Scanning identifies the tokens, parsing checks the syntax, validating checks the relation and attribute names against the catalog.
  • The code is executed directly (interpreted mode) or stored and executed later (compiled mode).
  • Short form (Week 05 slide 33): parsing and translation → optimization → evaluation.

2. From SQL to a query tree

  • SQL is declarative (what is wanted); relational algebra is procedural (how to get it) and has many equivalent expressions. So SQL is translated to RA, and the optimizer chooses a good equivalent expression.
  • Pipeline: English → SQL → relational algebra → query tree → execution plan (a tree with an algorithm chosen for every node).
  • Query tree: leaves are the input relations, internal nodes are RA operations. Execution starts at the leaves, each internal node is replaced by its result, and the root gives the answer.
  • Mapping: SELECT list → π, FROM → × (later ⋈), WHERE → σ.
  • Query block: one SELECT–FROM–WHERE expression (with GROUP BY / HAVING if any). A nested query is split into blocks: the inner block ℱ MAX Salary (σ Dno=5 (EMPLOYEE)) returns a constant c, the outer block is π Lname, Fname (σ Salary>c (EMPLOYEE)).

S3b (hashing) is crossed out on the slide.

4. Compound conditions

  • Conjunctive (AND): (a) use the index of one condition, then test the other conditions on the retrieved records; (b) use a composite index if the equality attributes match it; (c) with several secondary indexes that hold record pointers, intersect the pointer sets and fetch only the records in the intersection.
  • Disjunctive (OR): run a simple-condition algorithm for each disjunct, union the results and remove duplicates. If even one disjunct has no access path, the whole selection becomes a linear scan.

5. Projection and DISTINCT

  • Removing unwanted columns is done on the fly. Eliminating duplicates is the expensive step.
  • No DISTINCT → no duplicate elimination.
  • DISTINCT and a key is in the attribute list → no duplicates can exist → nothing more to do.
  • DISTINCT and no key in the list → sort the projected tuples, then remove adjacent repeated tuples.

6. Set operations

  • ∪, ∩ and − need union-compatible relations: same number of attributes, same attribute names, same domains.
  • Sorting-based algorithm: sort both relations on the same attributes, then merge in one pass. ∪ keeps one copy of a tuple found in both; ∩ keeps only tuples found in both; R − S keeps tuples of R that are not in S.
  • Cartesian product: R with n records and j attributes × S with m records and k attributes gives n × m records and j + k attributes. Very expensive — avoid it.

7. Three classes of operators (Week 04 slide 9)

  • Tuple-at-a-time unary (σ, π): no need to hold the whole relation in memory.
  • Full-relation unary (duplicate elimination, grouping): must see all or most tuples at once.
  • Full-relation binary (∪, ∩, −, ⋈, ×): must see the tuples of both relations.

Question 2.2Past examTested in 1 exam paperWhy SQL becomes relational algebra

Source: Past exam — 2021 SIS312, Q2(b), PDF pages 17–18 [1 mark]. (Exact wording. Official key available.)

Idea tested: Why SQL is translated into relational algebra

Appeared in: 1 verified exam paper — 2021 SIS312.

Exact or similar repetitions: Asked once.

Question:

“Why the SQL query is transformed into relational algebra in query optimization?”

Model answer
  • An SQL query is declarative: it says what to get, not how. It has no execution plan.
  • A relational algebra expression is procedural: it is a sequence of operations, so it tells how to do the query and has an associated execution plan.
  • A relational algebra expression has many equivalent expressions. Using the transformation rules, the optimizer can rewrite it and choose the cheapest equivalent form.

Official key: “SQL queries only tells us what to get but Relational algebra tells how to do the query. The relational algebra expressions may have many equivalent expressions.”

Question:

For the following two queries:

Query 1
Select Fname
From Employee
Where dno='3'
Query 2
Select distinct Fname
From Employee

  1. Which query has more cost? Why?

Model answer

Query 2 must also eliminate duplicates: Fname is not a key, so the same first name can appear several times. Question:

σ DNO=5 AND SALARY>30000 AND Gender=F (EMPLOYEE)

Explain how the selection is executed when there is:

  1. an index on DNO only;
  2. a composite index on (DNO, GENDER);
  3. secondary indexes with record pointers on DNO and on Gender.
  4. What changes if the three conditions are joined by OR and Salary has no index?
Model answer
  1. Use the index to retrieve the records with DNO = 5, then test Salary > 30000 and Gender = F on each retrieved record.
  2. Use the composite index to retrieve the records with DNO = 5 and Gender = F directly (both are equality conditions on the index attributes), then test Salary > 30000.
  3. Intersection of record pointers: get the pointer set for DNO = 5 and the pointer set for Gender = F from the two indexes, intersect them, fetch only the records in the intersection, then test Salary > 30000. Only data blocks that satisfy both indexed conditions are read. This needs record pointers, not block pointers.
  4. With OR every disjunct must be evaluated and the results unioned without duplicates. Because Salary > 30000 has no access path, the whole selection falls back to a linear scan. AND lets you pick the best index; OR needs an access path for every condition.

Aggregates, GROUP BY and Join Algorithms

B. Short Revision

1. Aggregates and the B-tree ⚠ MAX / MIN: 4 papers

COUNT, SUM, AVG, MAX and MIN work on a set of values and return a number. They do not need the whole row. For SELECT MAX(Salary) FROM EMPLOYEE;:

  • index on Salary → index scan, no data blocks;
  • no index, but the table is sorted on Salary → MIN and MAX are readily available at the two ends;
  • no index and not sorted → full table scan.
AggregateWith a B-tree index on the attribute
MAXtraverse till the right-most index key
MINtraverse till the left-most index key
SUM, AVGvisit all keys
COUNTusually part of the catalog, so it is found directly

Index-only query: a query answered from the index without reading the data file. It works when the index is dense and holds every attribute the query needs, e.g. MAX or MIN of the indexed attribute.

2. GROUP BY

Sorting method: sort the relation on the grouping attributes → partition it into groups → apply the aggregate to each group. With a clustering index on the grouping attribute the file is already grouped, so the sort is not needed.

4. Block nested-loop join — the repeated numerical problem ⚠ 7 papers

  • Outer relation: the relation of the outer loop. It is read once, one chunk at a time.
  • Inner relation: the relation of the inner loop. It is scanned completely once for every chunk of the outer relation.
  • Why the inner relation is scanned again and again: there is no index and no order, so every outer record must be compared with every inner record, and memory holds only one chunk of the outer relation at a time.
  • Buffers (slide: “Mbuff [outer, inner, result]”): of the nB buffers, one holds the current inner block and one holds the result block. The other nB − 2 hold the chunk of the outer relation.
outerouterouterouterinnerresult

nB = 6: four buffers for the outer chunk, one for the inner block, one for the result.

Cost = bOuter + ⌈ bOuter / (nB − 2) ⌉ × bInner   [ + (js × |R| × |S|) / bfrRS if the result is written ]

  1. Find the blocks of each relation: b = (number of records × record size) / block size.
  2. Put the smaller relation in the outer loop: fewer chunks, so fewer scans of the inner relation.
  3. Number of chunks = ⌈bOuter / (nB − 2)⌉. Round up.
  4. Cost = bOuter + chunks × bInner. If the question asks for the best way, compute both orders.
  • Minimum buffers = 3: one for the outer, one for the inner, one for the result (nB − 2 must be at least 1).
  • More buffers help only until the whole outer relation fits (nB − 2 ≥ bOuter); then the cost is bOuter + bInner.
  • Slide example: bR = 7, bS = 3, nB = 4. R outer: 7 + ⌈7/2⌉ × 3 = 19. S outer: 3 + ⌈3/2⌉ × 7 = 17. The Week 04 slides write “Buffers” for nB − 2.
Common mistakes. Dividing by nB instead of nB − 2 · forgetting to round the number of chunks up · putting the larger relation outside · using the selection cardinality in this formula (it is not needed) · saying one thing and computing another, as the 2015 key does (Question 3.2).

Question:

“Given two relations R and S such that the number of records in R is 100 000 records, each record is 500 bytes long. The number of records in S is 50 000 records, each record is 750 bytes long. A block is of size 5000 bytes. The selection cardinality is 200 and the number of available buffer space are 6.

a) Assume the nested loop method is used to compute R Join S and the join condition is R.A = S.B. Which one of the two relations is used in the inner loop. Calculate the number of block access assuming the cost of writing the join result back to disk is neglected. [3 marks]

b) What is the minimum number of memory buffer needed to do the join and why?” [2 marks in 2019]

Model answer

(a) Step 1 — blocks.

bR = (100,000 × 500) / 5,000 = 50,000,000 / 5,000 = 10,000 blocks
bS = (50,000 × 750) / 5,000 = 37,500,000 / 5,000 = 7,500 blocks

Step 2 — outer and inner. bS < bR, so the smaller relation S is in the outer loop and R is used in the inner loop.

Step 3 — cost. nB − 2 = 6 − 2 = 4 buffers hold the outer chunk, so S is read in ⌈7,500 / 4⌉ = 1,875 chunks, and R is scanned once per chunk.

Cost = bS + ⌈bS / (nB − 2)⌉ × bR = 7,500 + 1,875 × 10,000 = 18,757,500 block accesses

Check of the other order (R outer): 10,000 + ⌈10,000 / 4⌉ × 7,500 = 10,000 + 2,500 × 7,500 = 18,760,000. That is 2,500 more, so S outer is the right choice.

(b) Minimum = 3 buffers: one for a block of the outer relation, one for a block of the inner relation and one for the result (key: “3 buffers. One for R and one for S and one for the result”). The join still works, but it is far slower: 7,500 + 7,500 × 10,000 = 75,007,500 block accesses.

Why “selection cardinality = 200” is not used: a nested-loop join compares every block of S with every block of R, so the number of reads depends only on bR, bS and nB. The selection cardinality would be needed for a single-loop (index) join, or to estimate the size of the result — and the question says the cost of writing the result is neglected.

Convention check. The official keys compute b = total bytes / block size, which gives bS = 7,500. That matches the slides, where bfr = block size / record size with no rounding (Week 02 — Indexing, W2&3&4.pdf, slide 4 (PDF page 4)). If a grader insists on whole records per block: bfrS = ⌊5,000 / 750⌋ = 6, so bS = ⌈50,000 / 6⌉ = 8,334 and bR stays 10,000. Then S outer = 8,334 + 2,084 × 10,000 = 20,848,334 and R outer = 10,000 + 2,500 × 8,334 = 20,845,000, so R outer becomes slightly cheaper because of the rounding. Write the key’s answer (18,757,500) first.
Answer-key correction (minor): the keys write bS / (nB − 2) without the ceiling. The result is unchanged because 7,500 / 4 is a whole number; in general the division must be rounded up.

Idea tested: MAX / MIN using a B-tree index

Appeared in: 4 verified exam papers — 2014, 2021, 2021 SIS312, 2023.

Exact or similar repetitions: Exact repeat of the MAX sentence in 3 papers (2014, 2021, 2023); the 2021 SIS312 paper asks the same about MIN.

Question:

“How can a database execute the MAX aggregate operator using a B-Tree index?”

2021 SIS312 version: “How can a database execute the MIN aggregate operator using a B-Tree index?”

Model answer

MAX: traverse till the right-most index key. Start at the root and always follow the right-most pointer down to the last level; the right-most key there is the maximum.

MIN: traverse till the left-most index key. Follow the left-most pointer at every level; the left-most key is the minimum.

Why: the keys of a B-tree are kept in sorted order, smallest on the left and largest on the right. Cost: one block per level of the tree; the data file is not read.

Official keys: “Traverse till the right-most index key” (MAX); “Traverse till the left-most index key” (MIN). For the 2-mark version add the reason and the cost.

Source: Past exam — 2017, Q1, PDF page 7 [4 marks]. (Exact wording. No answer key in the PDF; the answer below is built from the slides.)

Idea tested: Dense and sparse indexes for aggregate operations

Appeared in: 1 verified exam paper — 2017.

Exact or similar repetitions: Asked once. Related: MAX / MIN with a B-tree (4 papers) and the index-only query (1 paper).

Question:

“Can a dense and sparse (non-dense) index answer all types of aggregate operations? If not how can we handle this to answer all aggregate operations?”

Model answer

A dense index can; a sparse index cannot do it alone.

  • Dense index on the attribute: it has an entry for every record, so it contains every value of the attribute. MAX (right-most key), MIN (left-most key), SUM and AVG (visit all keys) and COUNT can all be answered from the index alone.
  • Sparse index: it has only one entry per data block, so most values are not in the index. SUM, AVG and COUNT cannot be computed from it. MIN is the first entry; MAX needs the last data block, because the largest key is the last record of that block, not an index entry.

How to handle it:

  • go through the sparse index to the data file, which is sorted: MIN and MAX are at its two ends, and SUM / AVG need a scan of the data blocks; or
  • build a dense index (B-tree) on the aggregated attribute, so all aggregates are answered from the index;
  • COUNT is usually kept in the catalog, so it is found directly.

B. Short Revision

1. Two optimization techniques

Query optimization = rewriting a query into an equivalent one (same result set) that is better (costs less disk access, computation, memory). It is “not necessarily optimal, but reasonably efficient”.

What it doesapplies rules that re-order the operations of the query treeestimates the cost of different execution strategies and chooses the cheapest

Expected course answer ⚠ 4 papers Heuristic optimization is applied before cost-based optimization: heuristics decide the order of operations, then cost-based optimization selects the algorithm for each operation. The slides add that real systems use both techniques together.

2. The main heuristic

Apply first the operations that reduce the size of intermediate results:

  • apply σ and π as early as possible — σ reduces the number of tuples, π the number of attributes;
  • apply the most restrictive σ and the most restrictive ⋈ first;
  • avoid × if possible — combine it with a σ into a ⋈.

4. The six steps of heuristic optimization

  1. Break up every σ with a conjunctive condition into a cascade of σ operations.
  2. Move each σ down the tree as far as its attributes allow.
  3. Re-arrange the leaves so the relations with the most restrictive σ are executed first.
  4. Combine each × with the σ above it into a ⋈.
  5. Move π down the tree as far as possible, creating new π operations as needed.
  6. Identify sub-trees that can be executed by a single algorithm (pipelining).

Question 4.1Past exam⚠ Repeated in 4 exam papersHeuristics before cost-based?

Source: Past exam — 2014, Q5, PDF page 3 [1 point]; 2017, Q3, PDF page 8 [4 marks]; 2021, Q2(d) (printed as a second “b)”), PDF page 15 [2 marks]; 2015, Q8, PDF page 5 [2 points] (reversed wording). (Exact wording. Official keys: 2014 and 2015.)

Idea tested: Heuristic optimization before cost-based optimization

Appeared in: 4 verified exam papers — 2014, 2015, 2017, 2021.

Exact or similar repetitions: Exact repeat of the same sentence in 3 papers (2014, 2017, 2021). The 2015 paper reverses it: “after” instead of “before”.

Question:

“Is it practical to apply heuristic optimizations before cost-based optimization? Why or why not?”

2015 version: “Is it practical to apply heuristic optimizations after cost-based optimization? Why or why not?”

Model answer

Before: yes. After (2015): no.

  • Heuristic optimization decides the order of the operations. It rewrites the query tree with rules (σ and π moved down, × and σ replaced by ⋈). It needs no statistics, so it is cheap.
  • Cost-based optimization then selects the algorithm that carries out each operation of that tree, by estimating the cost of the alternatives from catalog statistics and choosing the cheapest.
  • Applying heuristics first makes the intermediate results smaller and leaves the cost-based step with fewer alternatives to estimate.
  • The reverse order is not practical: once the tree is re-ordered, the costs estimated for the old tree are no longer valid, so the cost-based work would be wasted.

Official keys: 2014 — “Yes it is. Heuristic optimizations should be applied before cost-based optimization. In heuristic optimization, the order of operations is decided and in cost-based optimization, which algorithm to carry out the operation is selected.” 2015 — “No, it is not.” followed by the same explanation.

For the 4-mark version (2017) give all four points. Precision: the slides say real systems use both techniques together; the expected exam answer is still “heuristics first”. Basis: Week 04 — Query Optimization Techniques, W2&3&4.pdf, slides 49–52 (PDF pages 148–151).

Model answer

Pushing π down removes the attributes that are not needed as early as possible. The tuples of the intermediate results become smaller, so more tuples fit in a block and the intermediate results occupy fewer blocks. B. Short Revision

1. What is counted

  • Cost components: I/O (blocks), storage, CPU, memory buffers, data transferred. The course counts I/O block accesses only.
  • Cost of an operation = finding the first block + reading all blocks with matching records. Blocks written are ignored in many cases.
  • The numbers are estimates from catalog statistics; the optimizer picks the plan with the lowest estimated cost.

Question 5.1Past examTested in 1 exam papersl, s, bfr and js

Source: Past exam — 2013, Q8, PDF page 1 [1 point]. (Exact wording. No answer key.)

Idea tested: Selectivity, selection cardinality, blocking factor and join selectivity

Appeared in: 1 verified exam paper — 2013.

Exact or similar repetitions: Asked once as definitions. The same quantities are needed in every cost calculation.

Question:

“Explain these keywords: selectivity (sl), selection cardinality (s), blocking factor (bfr), and join selectivity (js).”

Model answer
  • Selectivity (sl): the fraction of the records of a file that satisfy a condition, a number between 0 and 1. Equality on a key: sl = 1/r. Equality on a non-key attribute with d distinct, uniformly distributed values: sl = 1/d.
  • Selection cardinality (s): the average number of records that satisfy an equality condition on the attribute: s = sl × r.
  • Blocking factor (bfr): the number of records that fit in one block: bfr = block size / record size.
  • Join selectivity (js): the ratio of the size of the join result to the size of the Cartesian product: js = |R ⋈A=B S| / |R × S|, with 0 ≤ js ≤ 1. No join condition gives js = 1; no matching tuples gives js = 0.

Example with the lecture numbers: EMPLOYEE has r = 10,000 and bfr = 5, so b = 2,000. Dno has d = 125, so sl = 1/125 = 0.008 and s = 0.008 × 10,000 = 80. For EMPLOYEE ⋈ DEPARTMENT, js = 1/125, so the result has (1/125) × 10,000 × 125 = 10,000 records.

B. Short Revision

1. Transaction

  • Definition: a transaction is a sequence of database actions that is considered as a unit of work. Actions: read R(X), write W(X), commit, abort. It reflects one real-world transition that either happens completely or not at all (e.g. a money transfer).
  • In ad-hoc SQL each statement is one transaction; in a program several statements are grouped between START TRANSACTION and COMMIT.
  • It ends successfully by COMMIT (all its changes are reflected in the database) or unsuccessfully by ABORT (none of its changes are reflected).
  • write_item(X) changes X in a memory buffer; the block is stored back to disk “either immediately or at some later point in time”.

4. Concurrency and its problems

Many users share the database. Operations of different transactions are interleaved (one operation at a time, with context switches). Serial-only execution gives low throughput, long response time and poor resource utilization. All examples use X = 80, Y = 20, N = 5, M = 4.

Dirty read vs unrepeatable read: a dirty read is about uncommitted data that is then rolled back (one read is enough). An unrepeatable read needs two reads of the same item in one transaction, and happens even when the other transaction commits.

5. Schedules

  • A schedule S of n transactions is an ordering of the execution of their operations. Notation: r = read, w = write, c = commit, a = abort; in r1(X), 1 is the transaction and X the data item.
  • A serial schedule runs one transaction completely, then the next. It always keeps the database consistent.
  • Two operations conflict iff they (1) belong to different transactions, (2) access the same data item, and (3) at least one of them is a write. Types: read-write, write-read, write-write. A non-serial schedule with conflicting operations may cause inconsistency.
Proper (complete) schedule. It (1) contains all operations of all its transactions, and (2) keeps the operations of each transaction in the same order as in that transaction. The slides also mark a schedule as wrong when a transaction has an operation after it has terminated (after its commit or abort). An improper schedule is not classified — in a multiple-choice question it is never the answer.

6. Recoverable, cascadeless, strict ⚠ 6 papers

Look at every pair “T1 writes X … later T2 reads X” (write-read) and, for strict, also “T1 writes X … later T2 writes X” (write-write).

TypeDefinition (slides)Test
Recoverableno transaction commits until all transactions that wrote an item it read have committedfor each write-read pair, the writer terminates before the reader commits
Cascadelesstransactions read only items written by committed transactionsfor each write-read pair, the writer terminates before the read takes place
Stricttransactions read or write only items written by committed or aborted transactionsfor each write-read and write-write pair, the first writer terminates before the other operation takes place

Strict ⊂ Cascadeless ⊂ Recoverable  —  every strict schedule is cascadeless, every cascadeless schedule is recoverable; not the reverse.

  1. Proper? Check each transaction’s operations. If the schedule is improper, stop.
  2. Number the operations. For each item list the write-read and write-write pairs of different transactions.
  3. Dirty read = a read that comes before its writer’s commit. Any dirty read → not cascadeless (and not strict).
  4. For each dirty read compare the commits: reader commits before writer → not recoverable.
  5. No dirty read: check the write-write pairs. A write that comes before the first writer’s commit → not strict.
  6. State all three properties in the answer, each with its reason.
T1 writes X, then T2 …Result

Cascading rollback: an uncommitted transaction must roll back because it read an item written by a transaction that failed, e.g. r1(X); w1(X); r2(X); a1; a2;. Cascadeless schedules avoid it.

Common mistakes. Calling a read “dirty” when it comes before the write · checking only the commit order and forgetting where the read happens · forgetting write-write pairs for strict · answering only “recoverable” without the other two · classifying an improper schedule.

7. Conflict-serializability Outside the supplied slides ⚠ 2 papers

  • A schedule is conflict-serializable if it is conflict-equivalent to some serial schedule: the same operations, with every pair of conflicting operations in the same order.
  • Precedence graph: one node per transaction; draw an edge Ti → Tj when an operation of Ti comes before a conflicting operation of Tj. No cycle → conflict-serializable, and the equivalent serial orders follow the arrows. A cycle → not conflict-serializable.
  • It is a different property from recoverability: serializability is about the order of conflicting reads and writes; recoverability is about commits and aborts. A schedule can be strict and not serializable, or serializable and not recoverable (Question 6.3).

2021 and 2021 SIS312: “Explain briefly the transaction properties.”

Model answer

Transaction: a sequence of database actions (read, write, commit, abort) that is considered as a unit of work; it is either completed in its entirety or not done at all.

  • Atomicity: a transaction is an atomic unit of processing; it is either performed in its entirety or not performed at all.
  • Consistency preservation: a correct execution of the transaction takes the database from one consistent state to another.
  • Isolation: a transaction should not make its updates visible to other transactions until it is committed; its execution should not be interfered with by other transactions running concurrently.
  • Durability: once a transaction is committed, its changes must never be lost because of a later failure; they persist in the database.

Model answer

2013. A transaction is a sequence of database actions considered as a unit of work (done completely or not at all). The sketch is the diagram above: begin transaction → Active (read, write) → end transaction → Partially committed → commit → Committed → Terminated; abort from Active or from Partially committed → Failed → Terminated.

2019 / 2021 SIS312 — partially committed vs committed.

  • Partially committed: the transaction has executed its last operation, but its effects are not yet permanent — they may still be only in memory, not safely stored on disk. A failure at this point sends the transaction to Failed, and its changes are undone.
  • Committed: the commit has completed. The effects of the transaction are permanent: they are safely stored and will survive any later failure. The transaction can no longer be aborted.

Official keys: 2019 — “Partially committed the effect of the transaction is not saved yet to the disk, after it is safed to disk it is committed.” 2021 SIS312 — “Partially committed the effect of the results of the transactions is not yet stored in hard disk. Committed the effect of the transactions is permanent and stored in the hard disk.”

Answer-key correction (precision): the keys’ wording is what the exam expects, but “stored on the hard disk” is looser than the definition. What commit guarantees is durability — the changes are recorded safely enough to be recovered after a failure. It does not require that every changed data block has already been written; the slides themselves say a write is stored “either immediately or at some later point in time”.

B. Short Revision

1. Which T-SQL object?

ObjectUse it whenHow it runs

User-defined functionone value has to be computed and used inside queriesSELECT dbo.name(value); declared with RETURNS type

  • FOR INSERT is an AFTER trigger: when it runs, the new rows are already in the table, so a count includes them.

2. Mandatory access control (MAC)

Each individual gets a clearance and each document a classification, taken from ordered security classes: top secret (TS) > secret (S) > confidential (C) > unclassified (U). A person can access documents whose classification is equal to or lower than the person’s clearance.

Question:

“1. A report to retrieve the total number of registrations in a certain course is usually requested. Write a T-SQL object that can achieve that.”

Model answer

A report that is requested repeatedly with a parameter → a stored procedure (a scalar function is also accepted by the key).

CREATE PROCEDURE num_reg @cname VARCHAR(50)
AS
BEGIN
    SELECT COUNT(*) AS total_registrations
    FROM registeration AS r
    JOIN course AS c ON c.CID = r.cid
    WHERE c.cname = @cname;
END;
GO
EXEC num_reg @cname = 'Database Systems II';

Alternative — user-defined function:

CREATE FUNCTION num_reg_fun (@cname VARCHAR(50))
RETURNS INT
AS
BEGIN
    DECLARE @num INT;
    SELECT @num = COUNT(*)
    FROM registeration AS r
    JOIN course AS c ON c.CID = r.cid
    WHERE c.cname = @cname;
    RETURN @num;
END;
GO
SELECT dbo.num_reg_fun('Database Systems II') AS total_registrations;

Official key: create proc num_reg @cname varchar(5) as declare @num int select @num = count(*) from registeration, course where course.cid = registeration.cid and cname = @cname return @num [1 mark for the header, 1 mark for the query], or the same query inside create function num_reg_fun (@cname varchar(5)) returns int.

Both key versions work. Two small points: varchar(5) cuts any course name longer than five characters, so declare a longer parameter; and a procedure’s RETURN can only hand back an integer, which is fine for a count.

Question 7.2Past examTested in 1 exam paperTrigger: at most 6 courses

Source: Past exam — 2023, Q4.2, PDF page 23 [3 marks]. (Exact wording; same schema. Official key available — it contains errors.)

Idea tested: T-SQL trigger

Appeared in: 1 verified exam paper — 2023.

Exact or similar repetitions: Asked once (2023). It is the second part of the T-SQL question.

Question:

Consider the following schema:

department(DID, dname)
student(SID, sname, gpa, dept)      // dept is a foreign key from department(DID)
course(CID, cname, credit, dept)    // dept is a foreign key from department(DID)
registeration(sid, cid)             // sid is a foreign key from student(SID) - cid is a foreign key from course(CID)

“2. Maximum number of courses that a student can register in is 6. Write a T-SQL object that can achieve that.”

Model answer

A rule that must hold on every insert → a trigger on registeration.

CREATE TRIGGER max_reg
ON registeration
AFTER INSERT
AS
BEGIN
    IF EXISTS (
        SELECT r.sid
        FROM registeration AS r
        WHERE r.sid IN (SELECT sid FROM inserted)
        GROUP BY r.sid
        HAVING COUNT(*) > 6
    )
    BEGIN
        RAISERROR('A student cannot register in more than 6 courses.', 16, 1);
        ROLLBACK TRANSACTION;
    END
END;
  • Why > 6: an AFTER trigger runs when the new rows are already in the table, so the count includes them. Six courses are allowed; the seventh makes the count 7 and is rolled back.
  • Why IN (SELECT sid FROM inserted) with GROUP BY: one INSERT statement can add several rows, for one student or for several. Every affected student is checked.
  • ROLLBACK cancels the insert. Add UPDATE to the trigger events if a registration’s sid can be changed.

Official key: create trigger max_reg on registeration for insert as if ((select count(*) from registeration where sid = (select sid from inserted)) >= 3) begin print('max num of regis is 3') rollback end [1 mark header, 1 mark condition, 1 mark rollback].

Answer-key correction: the key checks 3, but the question says 6. Changing only the number is not enough: with >= 6 the sixth course would be rejected, because the trigger fires after the insert — the test must be > 6. Also, sid = (select sid from inserted) fails when a statement inserts more than one row. Corrected solution: the trigger above.

Model answer

Mandatory access control works by assigning a clearance to individuals and a classification to documents. A person with clearance level X can access documents whose classification level is equal to or less than X.

Security classes: top secret (TS), secret (S), confidential (C) and unclassified (U), where TS is the highest level and U the lowest: TS > S > C > U.

This is the official key. “Mandatory” means the rule is imposed by the system for everyone; users cannot pass the access on at their own discretion.
