Lesson 01

The big picture: the problem and the vocabulary

Before any algorithm, let's understand what a database is actually being asked to do, and why that is harder than it looks.

The problem in one sentence

From the lecture Problem: efficiently answering a given query.

A user (or an application) sends a query. The DBMS runs query processing and sends back a result. Simple, right? The catch is the word efficiently. A query over a table of millions of rows can be answered in a few milliseconds or in several minutes, depending entirely on how the DBMS decides to do the work.

Four terms from the lecture

From the lecture
  • The DBMS has algorithms to implement relational algebra expressions.
  • SQL is a different kind of high-level language: you specify what is wanted, not how it is obtained.
  • Optimization is not necessarily "optimal", but reasonably efficient. Techniques: heuristic rules + cost estimation.
  • Query optimization = the process of choosing a suitable execution strategy for processing a query.

1. "What, not how": declarative language

Imagine ordering food in a restaurant. You say "one grilled chicken, no onions" (what you want). You do not tell the chef which pan to use, in which order to chop things, or how hot the stove should be (how). SQL works the same way:

SELECT Lname FROM EMPLOYEE WHERE Dno = 5;   -- WHAT: last names of department 5

Nothing in this statement says "scan the file" or "use the index on Dno". Choosing that is the DBMS's job. Relational algebra, in contrast, is procedural: an expression like σ Dno=5 (EMPLOYEE) is already an ordered recipe of operations. Query processing is the translation from the "what" language to a "how" recipe.

2. "Algorithms to implement relational algebra"

Every relational algebra operator (select σ, project π, join ⋈, union ∪, …) must be implemented by a real piece of code that reads blocks from disk. For one operator there are usually several algorithms (selection alone has six in this lecture). Which one is best depends on what indexes exist and how the file is stored.

3. "Not necessarily optimal"

Think of a GPS app. Finding the mathematically best route among billions of possibilities would take so long that you would have arrived by car already. So the GPS settles for a very good route, fast. A DBMS does the same: the number of possible execution plans grows quickly, and the time spent searching for the perfect plan must not exceed the time saved. So the goal is reasonably efficient, not perfect.

4. The two techniques

Heuristic rules

Rules of thumb that almost always help, e.g. "do selections early, so later operations see fewer rows". They cost nothing to apply because no numbers are needed.

Cost estimation

Use statistics (number of rows, blocks, available indexes) to estimate how many block reads each candidate plan needs, then pick the cheapest.
No dumb questions
If SQL doesn't say how, who decides?
The query optimizer, a component inside the DBMS. You will meet it in Lesson 02.
Can two different plans give the same answer?
Yes, always. Plans differ only in speed, never in the answer. That is exactly what makes optimization legal: the DBMS may pick any equivalent plan.
Why should I care as a student or developer?
Because the plan the DBMS can build depends on what you gave it: indexes, sensible conditions, sorted files. This lecture shows which structure unlocks which algorithm.
Brain powerA table has 1,000,000 rows and you ask for the one row with Ssn = '123'. Name two very different ways the DBMS could find it. Which needs more disk reads, and why can't SQL tell the DBMS which to use?
SQL = WHAT
Optimizer = HOW
Lesson 02

The life of a query: from text to result

A SQL string is just text. Before a single block is read from disk, it passes through a small assembly line.

From the lecture Query evaluation process (typical steps when processing a high-level query): Query in a high-level language → scanning, parsing and validating → intermediate form of query → query optimizer → execution plan → query code generator → code to execute the query → runtime database processor → result of query.
The code can be executed directly (interpreted mode) or stored and executed later whenever needed (compiled mode).

Stage by stage

  1. Scanning breaks the text into tokens: SELECT, Lname, FROM, EMPLOYEE… This is like splitting a sentence into words.
  2. Parsing checks the grammar: is the order of keywords right? SELECT FROM WHERE EMPLOYEE fails here.
  3. Validating checks the meaning against the catalog (meta data): does table EMPLOYEE exist? Does it have a column Lname? Are types compatible?
  4. Intermediate form: the validated query is stored as an internal structure, normally a query tree (Lesson 04) or an equivalent graph.
  5. Query optimizer: uses heuristic rules + cost estimates to choose an execution plan: which algorithm to use for each operator.
  6. Query code generator: converts the plan into code the DBMS engine can run.
  7. Runtime database processor: runs that code, reads blocks, and produces the result.

Interpreted or compiled?

Interpreted mode

The generated code is executed directly, right now, once. Typical of an ad-hoc query you just typed into a console.

Compiled mode

The code is stored and run whenever needed, again and again, without redoing steps 1–6. Typical of a query embedded in an application (a stored procedure or prepared statement).
Example A banking app runs SELECT Balance FROM Account WHERE AccNo = ? a million times a day. Optimizing it once and storing the plan (compiled) saves a million repetitions of parsing and optimizing. A one-off report you type once is simply interpreted.
Watch it!Errors are caught at different stages. A misspelled keyword (SELCT) is a parsing error. A correct statement that names a table that doesn't exist (FROM EMPLOYE) is a validation error. Neither ever reaches the optimizer.
No dumb questions
The lecture shows this figure twice with different numbers (15.1 and 19.1). Are they different?
No. Same figure, taken from different editions of the textbook. Only the caption number changes.
Is the optimizer part of the DBMS or of my application?

Because that order wastes the least work. Filtering rows early means fewer rows to join; dropping columns last keeps the join columns available until they've been used.
Are the temporary names (StaffordOnly, PjD…) real tables?
No. They are just labels for intermediate results so the expression is readable.

Lesson 04

Query trees and how they are executed

An algebra expression becomes a picture: a tree. Reading the tree bottom-up tells you exactly what happens, in what order.

From the lectureQuery tree corresponds to a relational algebra expression.
  • Input relations (tables) → leaf nodes
  • Relational algebra operations → internal nodes
  • Execution (evaluation): starts at the leaf nodes; internal nodes are replaced by the result relation; ends at the root node.

How to run a tree: bottom-up replacement

  1. Find a node whose children are all leaves (already-existing tables). Here: node ① σ (child: PROJECT).
  2. Execute it; replace the node by its result. Now ① is a small temporary relation of 4 projects.
  3. Move up: node ② now has two available inputs (the 4 projects and DEPARTMENT). Execute, replace.
  4. Same for ③ with EMPLOYEE. Finally the root π keeps five columns. That output is the answer.
Example Row counts, step by step (PROJECT 200 rows, 4 in Stafford; DEPARTMENT 20; EMPLOYEE 10,000; each project belongs to exactly 1 department and each department has exactly 1 manager):
StepOperationRows inRows out
①σ Plocation='Stafford' (PROJECT)2004
②⋈ with DEPARTMENT4 + 204
③⋈ with EMPLOYEE4 + 10,0004
πkeep 5 columns44
Contrast with a careless plan: compute PROJECT × DEPARTMENT × EMPLOYEE first = 200 × 20 × 10,000 = 40,000,000 combined rows, then filter. Same answer, millions of times more work.
Key pointThe tree is not just a drawing. Different but equivalent trees (e.g. select pushed down vs. select at the top) give the same result with very different cost. Optimizers rewrite trees using heuristic rules, the classic rule being: apply selections (and projections) as early as possible.
Brain powerIn the tree above, what would happen to the 4-row intermediate results if the select σ were moved above node ③ instead of staying at ①? Count how many rows node ② would then have to produce.
No dumb questions
Why are tables always at the bottom?
Tables are your inputs; nothing produces them. Operators consume inputs and produce outputs, so data flows upward from leaves to root.
What do the numbers (1), (2), (3) on the slide mean?
The order of execution among operators. Smaller number = executed earlier.
What is the difference between a query tree and an execution plan?
The tree says which operations; the plan also says which algorithm carries out each one (e.g. "σ via index S6", "⋈ via nested loops").
Leaves = tables
Nodes = operators
Root = answer
Lesson 05

Query blocks and nested queries

Real SQL often has a query inside a query. The optimizer can't optimize a whole nested monster at once, so it cuts it into pieces.

From the lectureA query block contains a single SELECT-FROM-WHERE expression (along with ORDER BY, GROUP BY and HAVING, if any).

The lecture's example

SELECT LNAME, FNAME
FROM   EMPLOYEE
WHERE  SALARY > ( SELECT MAX(SALARY)
                 FROM   EMPLOYEE
                 WHERE  DNO = 5 );

In English: "List the employees who earn more than the best-paid employee of department 5." This text contains two query blocks, because there are two SELECT-FROM-WHERE units.

Example Department 5 salaries: 30,000 · 38,000 · 25,000 · 40,000. The inner block returns C = 40,000. The outer block then keeps every employee in any department with Salary > 40,000. If three employees earn 43,000, 55,000 and 40,000, the answer lists the first two; the one earning exactly 40,000 is not included because the condition is strictly ">".

Why does the optimizer split queries into blocks?

  • A block is the unit of optimization. The optimizer chooses an execution plan for each block separately. Each block is small enough that its plan can be searched sensibly.
  • The blocks are linked: results of an inner block are fed to the outer one, as above.
Watch it!Count blocks by counting SELECT … FROM … WHERE units, not by counting tables or keywords. The example uses the table EMPLOYEE twice, yet it is still exactly two blocks. And a plain query with GROUP BY and HAVING is still one block.
No dumb questions
Is the inner block always run once?
Here yes: it doesn't mention anything from the outer query, so its answer C never changes. (Nested queries that do refer to the outer row are called correlated and are costlier; the optimizer tries to rewrite them. That topic goes beyond this lecture.)
Why the funny F symbol?
ℱ is the algebra operator for aggregates (MAX, MIN, SUM, COUNT, AVG). Plain σ and π cannot compute a maximum.
Brain powerWhich index would make the inner block fast? Which would help the outer block? (Hint: look at the columns in each WHERE.)
1 SELECT-FROM-WHERE
= 1 query block

The currency of cost: counting block reads

To compare algorithms we need a ruler. In databases the ruler is the number of blocks transferred between disk and memory.

The questions evaluation must answer

From the lectureQuery evaluation:
  • How to evaluate an individual relational operation? Selection: find a subset of rows in a table. Join: connect tuples from two tables. Others: union, projection…
  • How to estimate the cost of an individual operation?
  • How does the available buffer affect the cost?
  • How to evaluate a whole relational algebraic expression?

The rest of the lecture answers the first question for σ, π and set operations. This lesson gives the tools for the second and third.

Why block reads?

Reading a block from disk takes milliseconds; the CPU can compare millions of values in the same time. So a plan that reads 12 blocks beats one that reads 3,000, even if the 12-block plan does more computing. You already know the unit of transfer is a block (page), holding several records.

How the buffer changes the picture

The DBMS keeps a buffer pool in main memory: a set of slots, each able to hold one disk block. If a block you need is already in a slot, reading it costs nothing from disk. Consequences:

  • Index blocks (small, used by every query) tend to stay in the buffer, so the top index levels are practically free. The lecture says it directly later: index blocks are small and often already in memory.
  • A table that fits entirely in the buffer can be scanned without disk reads after the first pass, which can make a linear scan cheap.
  • More buffer slots → fewer disk reads → lower real cost than the formulas predict. The formulas are therefore worst-case-ish estimates.
Watch it!Rounding is a favourite exam trap: bfr is rounded down (a record cannot be split across two blocks in this model) and b is rounded up (a partly-filled last block still occupies a whole block).
No dumb questions
Why is "found on average" half of b?
For a key the target exists once. It could be in the first block or the last, so on average the scan reads half the file before stopping. For a non-key, or when the value doesn't exist, the whole file must be read.
Does the DBMS really know r, b and x?
Yes: they are statistics kept in the catalog (meta data). They are what the optimizer plugs into cost formulas.

The select operator σ and its conditions

Selection is the star of today's lecture: "find a subset of rows in a table". Everything depends on what kind of condition you wrote.

From the lectureThe select operator σ produces a table containing a subset of the rows of the argument table that satisfy a condition. Same columns, fewer rows. Form: σ <condition> ( relation ).

Three shapes of condition

KindMeaningExample
Simpleone comparisonσ Dno=5 (EMPLOYEE)
Conjunctivecomparisons joined by ANDσ Dno=5 AND Salary>30000 (EMPLOYEE)
Disjunctivecomparisons joined by ORσ Dno=5 OR Salary>30000 (EMPLOYEE)
From the lectureSelection condition. Operators: <, ≤, ≥, >, =, ≠. A simple condition is <attribute> operator <constant> or <attribute> operator <attribute>. Conditions can be combined: <condition> AND <condition>, <condition> OR <condition>, NOT <condition>.

Equality vs. non-equality comparisons

Equality

Pnumber = 10
Finds records with exactly one value. Most index types handle this well.

Non-equality

Salary > 30000, Salary < 30000, Salary != 30000
Finds a range of values (or everything except one). Fewer structures handle this efficiently.

Each comparison has a comparison attribute (the column, e.g. Salary) and a comparison value (the constant, e.g. 30000). The lecture classifies every selection algorithm by three questions: which comparison type? which attribute (what access structure does it have)? how does the algorithm work?

Lesson 08

Access paths and the index families

A short refresher from the previous lecture: the lecture slides start the selection algorithms with this vocabulary.

From the lectureAccess path: a structure that makes searching for particular records efficient: indexes.
An index is a collection of (field value, pointer) entries.
  • Primary: ordered file · ordering key · block pointer
  • Clustered: ordered file · ordering field (non-key) · block pointer
  • Secondary: any file · any field · block or record pointer
  • B-Tree is the usual physical structure.

Think of a book

A file without an access path is a book without an index: to find "B-tree" you read every page. An index is the alphabetical list at the back: (term, page number). That's exactly an index entry: (field value, pointer). Whether you search the printed list quickly depends on whether it is sorted (it is) and short (it is, compared to the book).

Key pointTwo questions decide the index type: (1) is the file sorted on this field? (2) is the field a key (unique)? A file can be physically sorted in only one way, so it has at most one primary or clustering index, but any number of secondary ones.
No dumb questions
What's a "block pointer" vs. a "record pointer"?
A block pointer says "go to block 7" (then you search inside it). A record pointer says "block 7, slot 3": exact address. Primary and clustering indexes need only block pointers because they are sparse; secondary indexes use record pointers when they point to individual records.
Why does the slide say "B-Tree" under secondary?
Because a secondary index has one entry per record, it can be huge; the standard physical structure to store and search it (multilevel) is the B-Tree/B⁺-tree.

Lesson 10

S1 linear search and S2 binary search

The two algorithms that need no index at all. One always works; the other works only if the file is sorted.

S1: linear search (brute force)

From the lectureSimple condition algorithms. Comparison type: equality and non-equality. Comparison attribute: any (without any access structure). How: scan the data file, block by block, looking for records satisfying the comparison. aka: linear search / brute force.
S1 works on a heap file, on any field, for equality and non-equality alike. Any file, any condition, and always the slowest.

Linear search is what you do when you look for a name in an unsorted pile of paper forms: pick up form 1, check, put down, pick up form 2… The DBMS reads block 1, tests every record in it against the condition, keeps the matches, discards the rest, then reads block 2, and so on to the end of the file.

Example A tiny heap file of 12 records in 3 blocks (4 records per block). Condition: Dept_number = 3.
Block 195138 Block 2615317 Block 32111162
  1. Read block 1: test 9, 5, 13, 8: no match.
  2. Read block 2: test 6, 15, 3 ✓. Found one.
  3. If Dept_number is a key (unique), stop: 2 block reads. If it's a non-key, there might be more 3s, so you must keep going: read block 3 too: 3 block reads, the whole file.
Scaled up to the 3,000-block EMPLOYEE file: 1,500 reads on average for a key, 3,000 for a non-key or a value that doesn't exist.
Key pointS1 is the baseline: it needs nothing, works for any comparison, and every other algorithm must beat it to be worth using. For small tables, or when a large fraction of rows match anyway, S1 is often the right choice.

S2: binary search

From the lectureComparison type: equality. Comparison attribute: ordering key without an index. How: navigate the data file using binary search to locate the data block. Jump to the middle block, compare, discard half. Repeat. Requires the file to be physically sorted on the search field, so it helps for exactly one field.

It's the "guess the number" game: a friend thinks of a number from 1 to 100; you ask "higher or lower than 50?" and halve the range each time. A sorted file lets the DBMS do the same with blocks: look at the middle block; because the file is sorted, the target must be either entirely before or entirely after it, so half the file is eliminated with one read.

cost(S2) ≈ ⌈ log₂ b ⌉ block readsb = 3,000 blocks → ⌈log₂ 3000⌉ = ⌈11.55⌉ = 12 reads, versus 1,500 on average for S1.
Watch it!Binary search needs a file physically sorted on the very field you search. A file sorted by Ssn can't be binary-searched on Lname. That's why the lecture says it "helps for exactly one field". On a heap file binary search is meaningless: nothing guarantees that the target lies on one side of the middle.
Brain powerIf the file is sorted and has a primary index, the index lookup costs about 3 reads (b = 3,000) while binary search on the data costs 12. Why is the index cheaper, given both use the same sorted data?
No dumb questions
Why does S2 apply only to equality in the lecture?
The lecture's S2 locates one exact value. (A sorted file can in principle serve range queries too: locate the boundary, then read onward. That idea is formalized as S4 once an index exists.)
Is a "heap file" the same as an "unsorted file"?
Yes: records are stored in arrival order, with no organization.

S3a primary index and S4 ordering index

Now we add an index on a file that is sorted on a key: the best case in the whole lecture.

S3a: primary index, equality

From the lectureComparison type: equality. Comparison attribute: key with primary index. Example: σ Name='Allen, Troy' (EMPLOYEE). How: navigate the index to locate the index record with the comparison value.

The data file is sorted by Name. The primary index is sparse: it keeps one entry per block, namely the first record of that block (the block anchor). The six anchors in the lecture's picture:

Watch it!Sparse ≠ "only some records are findable". Every record is still reachable; the index just points to the block where the record must be if it exists. And the whole scheme is valid only because the file is sorted on the same key.

S4: ordering index, non-equality

From the lectureComparison type: non-equality. Comparison attribute: key with primary index. Example: σ empno>100 (EMPLOYEE). How: navigate the index to locate the data block with the corresponding equality condition, then retrieve preceding or subsequent records.

Because the file is sorted, all records with empno > 100 sit together at the end, and all with empno < 100 sit at the beginning. So: use the index to find where 100 lives, then walk the file in one direction.

Example EMPLOYEE: empno = 1…30,000 (unique), 10 per block → 3,000 blocks.
  • empno > 100: index → block 10 (holds 91–100). Matches start at block 11 and run to the end: 2,990 data blocks + the index reads. Result: 29,900 records.
  • empno ≤ 100: read blocks 1–10 only: 10 blocks, no index needed. Result: 100 records.
Watch it!S4's cost depends on how many records match, not on the index. If the range returns 99% of the file (as in "empno > 100"), S4 reads nearly as much as S1. Indexes help most when the answer is a small part of the table.

Lesson 13

Conjunctive conditions (AND)

Real queries rarely have a single condition. With AND, you only need to find a way to satisfy one of them cheaply; the rest can be checked afterwards.

Our running query: σ DNO=5 AND SALARY>30000 AND Gender='F' (EMPLOYEE). A record qualifies only if all three hold. Logic gives us a gift: any record in the answer must satisfy DNO=5. So we can use a fast path for that one condition and throw everything else away afterwards.

Strategy A: one index, then filter

From the lectureWhen: a comparison attribute with an index. Example: DNO=5 AND SALARY>30000 AND Gender=F; assume an index on DNO. How: use the index to retrieve satisfying records; apply the remaining comparisons.

Key pointIf several conjuncts have an access path, choose the most selective one (the one that returns the fewest records), because that leaves the least to filter. The optimizer uses statistics to decide.

Strategy B: a composite index

From the lectureWhen: a group of comparison attributes with a composite index appears in equality comparisons. Example: DNO=5 AND SALARY>30000 AND Gender=F; assume a composite index on (DNO, GENDER). How: use the composite index to retrieve satisfying records; apply the remaining comparisons.

A composite index is sorted by Dno first and, inside each Dno, by Gender, like a phone book sorted by last name then first name. The pair (5, 'F') is found directly. Only Salary>30000 is left to check, and only on records already known to satisfy the other two.

Watch it!The composite index here helps because both indexed columns are compared with equality. It can't serve a condition on Salary at all (not part of the index), and column order matters: an index on (Dno, Gender) can't efficiently answer "Gender='F'" alone.

Strategy C: intersection of record pointers

From the lectureWhen: comparison attribute(s) with secondary index(es) with record pointers. How: use the secondary index(es) to retrieve the record pointers; intersect the record pointers; retrieve the records and apply the rest of the comparisons.
From the lectureWhy this wins: index blocks are small and often already in memory; data blocks are large and on disk. Intersecting the pointer sets first means you only ever touch data blocks that satisfy every condition. Requires record pointers, not block pointers.
Example30,000 employees. Dno=5 matches 1,000; Gender='F' matches 15,000; both together ≈ 500.
  • Strategy A with only the Dno index: fetch up to 1,000 records (possibly 1,000 data-block reads), then filter.
  • Strategy C: read the pointer lists (1,000 pointers ≈ 10 index blocks; 15,000 pointers ≈ 150 index blocks at 100 per block), intersect in memory, then fetch only the 500 survivors: ≈ 160 index + 500 data reads ≈ 660 vs ≈ 1,010. It pays off when each condition alone matches a lot but together they match few.
Watch it!Why record pointers? A block pointer says "somewhere in block 3". If Dno=5 has a record in block 3 and Gender='F' has a (different) record in block 3, the block pointers "match" but no single record satisfies both. Only exact record addresses prove it's the same record.

Lesson 14

Disjunctive conditions (OR)

With OR, logic works against us: a record qualifies if it satisfies any one condition, so you must find all of them.

From the lectureDisjunctive conditions (OR):
  • Every disjunct must be evaluated: a record satisfying any one of them belongs in the result.
  • So: run a simple-condition algorithm on each disjunct, union the results, and remove duplicates.
  • If even one disjunct has no access path, the whole query falls back to a linear scan.
  • AND lets you pick the best index. OR forces you to use them all, or none.

Why can't we just use one index?

Take Dno=5 OR Salary>30000. An index on Dno finds the Dno=5 people. But a department-7 employee earning 50,000 also qualifies, and no Dno index will ever find them. Each disjunct contributes records the others miss, so every disjunct must be searched.

Example σ Dno=5 OR Ssn='123' (EMPLOYEE). Dno=5 returns 4 records (r12–r15); Ssn='123' returns r14, which happens to live in department 5 as well. Union with duplicates would list r14 twice. After duplicate removal, the answer has 4 records. In a relation, a record is either in the result or not; it can't appear twice.
Now change it: Dno=5 OR Salary>30000 where Salary has no index. Disjunct 2 has no access path, so you'd have to scan the whole file anyway to evaluate it, and while scanning you might as well test both conditions at once. Result: one S1 pass; the Dno index is never used.

How are duplicates detected?
By comparing the record's pointer (address): the same record has the same pointer. Sorting the pointers makes duplicates adjacent, which is exactly the idea reused in the next lesson.

Projection and duplicate elimination

Select removes rows. Project removes columns. Sounds trivial, until duplicates appear.

From the lectureThe project operator produces a table containing a subset of the columns of its argument table: π <attribute list> (relation). The result is a table, so tuples are unique (no duplicates). Example: π Name,Hobby (Person) ≡ SELECT Name, Hobby FROM Person.

Two jobs hidden in one operator

  1. Remove unwanted columns "on the fly": as each record is read, just copy the wanted fields. Easy.
  2. Eliminate duplicate tuples that this creates. "This step is the difficult one!"

Lesson 16

Set operations: ∪, ∩, − and ×

Union, intersection, difference and Cartesian product treat relations as sets of rows.

Cartesian product: the one to avoid

From the lectureThe CARTESIAN PRODUCT of relations R and S includes all possible combinations of records from R and S. The attributes of the result include all attributes of R and S. If R has n records and j attributes and S has m records and k attributes, the result has n × m records and j + k attributes. It is very expensive and should be avoided if possible.
ExampleR = 1,000 employees (6 columns), S = 200 projects (4 columns). R × S = 1,000 × 200 = 200,000 rows with 6 + 4 = 10 columns. Add a third table of 20 departments: 4,000,000 rows. Almost all of them are meaningless pairings, which a join condition would discard. That's why the optimizer turns "× then σ" into a join.

Union compatibility

From the lectureSet operations apply to type-compatible relations: the same number of attributes, the same attribute names (as the lecture phrases it), and the same attribute domains. Person(SSN, Name, Address, Hobby) and Professor(Id, Name, Office, Phone) are not union compatible, but π Name (Person) and π Name (Professor) are, so π Name (Person) − π Name (Professor) makes sense.
Watch it!Compatible means the columns line up (count and type). Compatibility is not about the number of rows. Projecting both sides to a common column list is the usual way to make two tables compatible.

Sorting-based algorithms

From the lecture UNION: sort both relations on the same attributes; scan and merge both sorted files concurrently; when the same tuple exists in both, keep only one.
INTERSECTION: sort both; scan and merge; keep only tuples that appear in both.

A good answer covers the points below; wording can differ.

71SQL is declarative: it states what result is wanted, not how to get it. Relational algebra is procedural: an expression is an ordered recipe of operators, and the DBMS has algorithms to implement each operator. Query optimization is the process of choosing a suitable execution strategy for a query. It uses heuristic rules (rules of thumb such as applying selections early) and cost estimation (using statistics to estimate block reads of candidate plans). It is not necessarily optimal because searching all possible plans would itself cost more than it saves, so the goal is a reasonably efficient plan, like a GPS that gives a very good route quickly rather than the mathematically best one.
72(1) The query in a high-level language is (2) scanned, parsed and validated (tokens, grammar, then names and types checked against the catalog), giving (3) an intermediate form (e.g. a query tree). (4) The query optimizer chooses (5) an execution plan. (6) The query code generator produces (7) code to execute the query, which (8) the runtime database processor runs to produce (9) the result. In interpreted mode the code is executed directly; in compiled mode it is stored and executed whenever needed, avoiding repeated parsing and optimizing (useful for queries embedded in applications).
73SQL: SELECT Fname, Lname FROM Employee AS E, Department AS D WHERE D.Dname='Research' AND D.Dnumber = E.Dno;
Algebra: ResDept ← σ Dname='Research' (Department); Joined ← ResDept ⋈ Dnumber=Dno Employee; Result ← π Fname, Lname (Joined).
Tree: leaves Department and Employee; σ above Department (1), ⋈ above σ and Employee (2), π at the root. Execution: start at the leaves, run σ (1), replace it by its result, run ⋈ (2), then π at the root, which produces the answer. The selection is placed first so fewer rows enter the join.
74A query block is a single SELECT-FROM-WHERE expression (with ORDER BY, GROUP BY, HAVING if any); it is the unit the optimizer handles separately. This query has two blocks. Inner: SELECT AVG(Salary) FROM Employee WHERE Dno=4 → ℱ AVG Salary ( σ Dno=4 (Employee) ), producing one value C. Outer: SELECT Lname FROM Employee WHERE Salary > C → π Lname ( σ Salary>C (Employee) ). The inner block runs first and feeds the constant C to the outer block.
75S1 linear search: always applicable; scans every block testing each record. S2 binary search: file sorted on the field, equality; halves the file repeatedly (≈ log₂ b reads). S3a primary index: equality on the ordering key; search the sparse index for the last anchor ≤ the value, then read one data block (x + 1). S4 ordering index, non-equality: >, <, ≥, ≤ on the ordering key; find the boundary block, then read onward (or from the start for </≤). S5 clustering index: equality on a non-key ordering field; the index points to the first block with the value, then read the following blocks while it matches (x + ⌈s/bfr⌉). S6 secondary index (B⁺-tree): any field with a secondary index; walk the index; for a non-key follow every record pointer (up to x + s).
76(A) One index, then filter: use an index on one conjunct to fetch records, then test the remaining comparisons on them in memory; pick the most selective conjunct. (B) Composite index: when equality comparisons cover the composite's attributes (e.g. (DNO, GENDER)), retrieve with it and test the rest. (C) Intersection of record pointers: use several secondary indexes, get one pointer list per condition, intersect them (e.g. {r2,r5,r7,r9} ∩ {r1,r5,r7,r8} = {r5,r7}), and fetch only those records, then test remaining conditions. Index blocks are small and often in memory; data blocks are large and on disk, so reading only survivors saves disk I/O. Record pointers are needed because block pointers can't show that the same record satisfies both conditions: two different records may simply live in the same block.
77With AND, every answer record satisfies every conjunct, so one good access path finds a small candidate set that is then filtered. With OR, a record belonging to the answer may satisfy only one disjunct, so every disjunct must be searched: otherwise records would be missed. Algorithm: run a simple-condition algorithm (S1–S6) on each disjunct, union the results and remove duplicates (a record may satisfy several disjuncts). If even one disjunct has no access path, finding its matches already needs a full scan, so the whole query is answered by linear search (testing all disjuncts per record). In short: AND lets you pick the best index; OR forces you to use them all, or none.
78Projection removes unwanted columns on the fly and may create duplicate rows. Without DISTINCT, duplicates are kept: no extra work. With DISTINCT and a key in the attribute list, duplicates are impossible: no extra work. With DISTINCT and no key in the list, duplicates must be removed: sort T′ on all attributes so equal tuples are adjacent, then scan with two indexes: output T′[i], advance j while T′[i] = T′[j] (and j ≤ n), then set i ← j, j ← i + 1, until i > n. Cost is dominated by the sort (≈ n log n).
79Relations must be union compatible (same number of attributes, same domains/names). Sort both on the same attributes and merge them with two pointers i (R) and j (S). Union: R<S output R, i++; R>S output S, j++; equal: keep one (j++); append leftovers. Intersection: output only when equal; advance the smaller; no leftovers. Difference R−S: output R(i) when R(i) < S(j); equal: skip both; append leftover R. The merge is one pass after the sort. The Cartesian product yields n×m records and j+k attributes (e.g. 1,000 × 200 = 200,000 rows), very expensive, so the optimizer replaces × plus selection by a join.
80S5 (clustering, file sorted on the field): all matches are adjacent, cost x + ⌈s/bfr⌉. S6 (secondary index, file not sorted on it): matches are scattered, so each pointer may cost a block read: up to x + s. Example: s = 20 matches, bfr = 10, x = 2: S5 = 2 + 2 = 4 reads; S6 up to 2 + 20 = 22. S6 can be worse than S1 when s is large: if 20,000 of 30,000 records (b = 3,000 blocks) match, following up to 20,000 scattered pointers could cost far more than scanning 3,000 blocks. The optimizer therefore needs statistics about how many records a condition matches.
