Lesson 01

The big picture: why do we need indexes?

Before we talk about indexes, let's see where they live and what problem they solve.

Where does a query go?

When you use an app (a website, a mobile app, a banking program…) and it needs data, it sends a query (a question, usually written in SQL) to the DBMS, the Database Management System. The DBMS is the software that manages the database, for example SQL Server, Oracle or MySQL. The DBMS finds the answer in the database and sends back a result.

No dumb questions
What is a "relation"?
It is the formal (mathematical) name for a table. A relation = a table, a tuple = a row, an attribute = a column. You'll see both sets of words in database courses.
What is "meta data"?
"Data about data." The table holds your actual data (students, orders…). Meta data describes it and helps the DBMS work with it: what tables exist, what indexes exist, statistics about how many rows there are, etc.

What is the problem?

From the lecture Objective: Effectively and efficiently answering a given query.
  • Effective: the accuracy of the query results (is the answer correct?).
  • Efficient: the response time (how fast did the answer come back?).

✔ Effective = correct

You asked for the student with ID 8734291 and you got that student, not someone else, not nothing.

⚡ Efficient = fast

You got the answer in a few milliseconds, not after a minute of waiting.

Indexes are mainly about efficiency: they make the DBMS find the correct answer much faster. (But as you'll see in Lesson 04, a wrongly used index can even break effectiveness!)

Lesson 02

How data lives on disk: files, records & pages

To understand indexes you first need to know how a table is physically stored. Good news: it's simpler than it sounds.

Tables become files, rows become records

From the lecture
  • A database table is mapped to physical file(s).
  • A database row is mapped to file record(s).
  • The smallest unit of data transfer is a block/page.
  • Typically, a block/page contains multiple records.
No dumb questions
Block or page: what's the difference?
For this course, treat them as the same thing: a fixed-size chunk of storage that is read or written in one go. "Block" is the operating-system / disk word, "page" is the database word. In SQL Server, one page = 8 KB.
Why can't the disk just give me one record?
Disks and SSDs physically move data in blocks. Reading one byte costs almost the same as reading the whole block, so the DBMS always reads whole pages.

What happens when you INSERT, DELETE or UPDATE?

1Find the blocks / pages that are involved.
▼
2Load them into memory (RAM).
▼
3Do the operation (in memory).
▼
4Save it to disk: the Log Data File (LDF) or the Master Data File (MDF).

In SQL Server, a database has an .mdf file (the main data file holding tables and indexes) and an .ldf file (the transaction log that records changes).

Blocking factor (bfr)

How many records fit into one block? That number has a name: the blocking factor.

bfr = Block Size ÷ Record SizeRound down: a record can't be cut in half across two blocks (in this simple model).
Example Block size = 4096 bytes, record size = 100 bytes.
bfr = 4096 ÷ 100 = 40.96 → 40 records per block (round down).
If the table has 30,000 records, it needs 30,000 ÷ 40 = 750 blocks (round up here: a partly-filled last block is still a block).
Records per block: round DOWN.
Number of blocks: round UP.

Two ways to organise a file

🗃️ Heap file

An un-organized space where records are kept without any clear order. New records are just dropped wherever there is room, like papers thrown on a pile.

Block 1701090 Block 23010040

Finding a value? You may need to look at every block.

📂 Sequential (ordered) file

Records are stored in an organized order (SEQUENTIAL) based on some field, like neatly labelled folders.

Block 1103040 Block 27090100

The field the file is sorted on is called the ordering field.

Why the database thinks in pages

✗ NOT like this

"Give me byte number 7,834,291."

✔ LIKE this

"Give me the whole PAGE that has it."

① Hardware reads blocks

Disks and SSDs move data in blocks. Reading one byte costs almost the same as reading a whole block.

② One read, many keys

A single 8 KB page can hold hundreds of keys. So one read removes a huge part of the search.

③ Simple mapping

One tree node = one page. Reading, writing and splitting become easy to manage.
Key pointWe don't design an index to look nice in RAM. We design it to reduce the number of page I/O (page reads and writes).
I/O = Input/Output = reading from or writing to disk.
Brain powerComparing two numbers in the CPU is extremely fast, like checking your pocket. Reading a page from disk is much, much slower, like walking to a shop. If you had to find something, would you rather make 4 trips to the shop or 24? That's the whole reason indexes are designed around pages.
Lesson 03

What exactly is an index?

From the lectureIndexing is the principal technique used to efficiently answer a given query.

The book analogy

An index for a database is like the index at the back of a book:

  1. It is smaller than the book.
  2. The words are in sorted order.
  3. If we are looking for a particular topic we first search the index, find the pages where it is discussed, then go to the actual pages in the book.

A book has 500 pages. To find "Photosynthesis" you can read every page, or open the index at the back, see "page 214" and go straight there. A database index does exactly this for rows.

Example from the lecture Table: MovieStar(Name, Address, Gender, Birthdate) 
SELECT * FROM MovieStar WHERE Name = 'Jim Carrey';
If there is no index on Name, all the blocks of the MovieStar relation must be inspected and visited. With an index on Name, the DBMS looks up "Jim Carrey" in the (small, sorted) index and jumps directly to the right block.

The formal definition

From the lecture
  • An index is an auxiliary file structure (an extra, helper file, separate from the data file).
  • Indexes are created on one or more columns of a table.
  • An index is created for specific field(s), usually the field(s) that appear in the WHERE clause of SQL queries.
  • An index speeds up searches, but it slows down other DML operations (INSERT, UPDATE, DELETE).
  • Changes in the data MUST be followed by index change and refreshment.
No dumb questions
What is DML?
Data Manipulation Language: the SQL commands that change data: INSERT, UPDATE, DELETE (and SELECT to read it).
Why does an index slow down INSERT/UPDATE/DELETE?
Because the index is a copy of some of the data, kept in sorted order. Every time the table changes, the index must also be changed so it stays correct. More work per change = slower changes. (Lesson 13 shows exactly how much.)
What does "search key" mean?
The column (or columns) the index is built on: the value you search by. It doesn't have to be the table's primary key; "key" here just means "the thing we look up".

Indexes as access paths

An access path is a route the DBMS can take to reach the data. A full scan is one access path; an index is a much shorter one.

  • The index file usually occupies considerably fewer disk blocks than the data file, because its entries (just key + pointer) are much smaller than full data records.
  • An index is always sorted on the index field(s).
  • A binary search on the index yields a pointer to the file record.
  • Indexes can be DENSE or SPARSE (next lesson!).

Binary search in 30 seconds

Binary search works on sorted data. Look at the middle; if your value is bigger, throw away the left half; if smaller, throw away the right half. Repeat. Each step removes half of the data.

Lesson 04

Dense vs. sparse indexes

Both are indexes. The only difference is how many entries they keep.

From the lecture
  1. Dense: one entry in the index file for every record (every search-key value) in the data file.
  2. Sparse (or NON-DENSE): one entry in the index file for each block of the data file, so it has entries for only some of the search values.

More facts about sparse indexes

From the lecture
  • A sparse index contains index records for only some search-key values: some keys in the data file will not have an entry in the index file.
  • Applicable when records are sequentially ordered on the search key (ordered files).
  • Normally keeps only one key per data block.
  • Less space (so more of the index can be kept in memory).
  • Less maintenance overhead for insertions and deletions.

When does sparse work?

A sparse index has no entry for most records. It relies on a promise: "everything between my entry 50 and my entry 90 is inside block 2." That promise is only true if the data is sorted on the search key.

Key pointA sparse index works well when the data file is ordered on the search key. If the data is not ordered, use a dense index (one entry per record).
Watch it!Remember Lesson 01's "effective vs efficient"? A sparse index on unsorted data doesn't just get slower, it gives a wrong result. That's a failure of effectiveness (accuracy), not just efficiency.
Lesson 05

The map of index types

Your lecture lists these types. Get the big map in your head first; the most important ones get their own lessons next.

Single-level indexes

1. Primary index

Automatically created on the primary key; ensures uniqueness.

2. Unique index

Ensures all values in the column(s) are unique (e.g. no two users with the same email).

3. Clustered index

Sorts and stores the data rows physically in order of the key. One per table.

4. Non-clustered index

Stores pointers to the data rather than the actual rows. Multiple allowed.

5. Composite index

Built on multiple columns, e.g. (LastName, FirstName).

6. Bitmap index

Efficient for low-cardinality columns: columns with few distinct values, e.g. gender.

7. Full-text index

Used for searching text fields efficiently (words inside articles, descriptions…).

8. Spatial index

Used for location-based / geospatial queries ("restaurants within 2 km").

9. Hash index

Uses hash tables for very fast equality lookups (WHERE x = 5).

Multi-level indexes

1. B-tree

A balanced, multi-level tree index (Lessons 10–12).

2. B+ tree

A B-tree variant whose leaves are linked together, great for range queries.
Text → Full-text
Map/location → Spatial
Few values → Bitmap
Exact "=" only → Hash
Many columns → Composite
No dumb questions
What is "cardinality"?
The number of distinct values in a column. Gender has low cardinality (few values). National ID number has high cardinality (every value different).
What is a bitmap?
A row of bits (0/1). For a gender column, a bitmap index keeps one bit-string per value, e.g. "Male: 1 0 0 1 1 …" meaning rows 1, 4, 5 are male. Very compact when there are few values.
What is a hash?
A function that turns a value into a "bucket number". Same value → same bucket, so an exact match is found almost instantly. But hashing scrambles order, so it's not good for ranges like "between 100 and 200".
Why only one clustered index per table?
Because rows can't be stored in two different physical orders at the same time, just like a bookshelf can't be sorted by author and by colour at once.
Lesson 06

Primary index

From the lecture
  • An index on a sequential (ordered) file: the index is associated with a data file that is itself sorted on the search key.
  • Usually used when the search key is also the primary key of the relation.
  • Usually, these indexes fit in main memory.
  • An index file record = (field value, block pointer).
  • How many primary indexes can we build for a data file? One primary index per data file.
Brain powerIn this example, is the primary index dense or sparse? (Think before reading the answer below.)

Answer: Sparse. There is one entry per block, not per record. "Abbot, Diane" has no entry of its own; we find her by going to the "Aaron, Ed" block and looking inside.
Key pointPrimary index = sorted data file + ordering field is a key (unique) + entries (key value, block pointer) + one entry per block (sparse) + only one per file.
Number of index entries = number of data blocks.
No dumb questions
Why only one primary index per file?
A primary index needs the data file to be physically sorted on its field. A file can be physically sorted in only one way, so only one such index is possible.
Why does it usually fit in main memory?
It only has one small entry per block. If a block holds 40 records, the index has 40 times fewer entries than the table has rows, and each entry is tiny.
Lesson 07

Clustering index

What if the file is sorted on a field that is not unique, like department number? Then we use a clustering index.

From the lecture
  • For sequential (sorted) data files.
  • Based on the ordering field: not necessarily unique, but must be not null.
  • An index file record = (field value, block pointer).
  • For every distinct ordering-field value → one index record.
Key pointClustering index: sorted file, ordering field is a non-key (repeats allowed, but NOT NULL), one entry per distinct value. It is usually sparse (fewer entries than records).
Watch it!Primary and clustering indexes both need the file physically sorted. A file can be sorted on only one field, so a file has either a primary index or a clustering index, not both.
Lesson 08

Secondary index

The file can only be sorted one way. But we want fast searches on other columns too. Solution: secondary indexes.

From the lecture
  • For any data file type (sorted, unsorted, heap…). The data is not sorted on the indexing field.
  • Secondary indexes facilitate query-answering on any attributes (PK or not, but not null).
  • The indexing field is not necessarily the ordering field.
  • A file can have several secondary indexes. → How many? Many.
  • A secondary index is dense. → It must be dense.
  • More than one data block may be needed for a given search key, so in general more disk I/O to answer queries: secondary indexes are less efficient than primary indexes.

Secondary index on a non-key field

If the indexed field repeats (e.g. Dept_number on an unsorted file), one value points to many records. A common solution adds an extra level of indirection: each index entry points to a block of record pointers, and that block lists every record with that value.

Clustered vs. non-clustered index

These words describe physical storage (how rows sit on disk). They're the words used in SQL Server.

Clustered index

Defines the physical order of the data in the table. Only one per table (rows can't be stored in two different physical orders).

Example: a clustered index on EmployeeID means rows are stored in ascending order of EmployeeID.

Page 1123Page 2456

The table IS the index.

Non-clustered index

A separate structure (like a lookup table) holding the indexed column(s) + a pointer to the actual row in the clustered index (or in the heap, if there is no clustered index). Many allowed per table.

Example: a non-clustered index on LastName creates a sorted list of last names with pointers to the actual employee rows.

It is not necessarily created over unsorted values.

A separate "phone book" pointing to the table.

Primary vs. secondary index (the SQL-world view)

Primary index

Created automatically on the primary key (often clustered by default). Ensures uniqueness and usually defines the row storage order.

Secondary index

Any index that is not the primary index. It can be clustered or non-clustered, depending on implementation. Typically refers to an extra lookup path on a non-primary attribute.
Key difference: secondary vs non-clustered
  • Secondary index is a logical concept → any index besides the primary one (could be clustered or non-clustered).
  • Non-clustered index is a physical storage structure → it doesn't change row order, it just stores a mapping.
In practice (especially in SQL databases): most secondary indexes are non-clustered, because the primary one is usually clustered. But not all secondary indexes are necessarily non-clustered.
Logical question: "Is it the primary one?"
Physical question: "Does it decide row order?"
Lesson 10

Multilevel indexes

An index makes searching the table fast. But what if the index itself becomes huge? Simple: build an index for the index.

From the lecture
  • Used when the index file is too large to fit in memory.
  • Because a single-level index is an ordered file, we can create a primary index to the index itself.
    • The original index file is called the first-level index; the index to the index is called the second-level index.
  • We can repeat the process, creating a third, fourth, …, top level until all entries of the top level fit in one disk block.
  • Result: faster search, but slower updates.

A two-level primary index

Key pointEach level reduces the search by a factor equal to the number of entries per block (called the fan-out). With a fan-out of 500, two levels already reach 500 × 500 = 250,000 blocks.

Multilevel index = a search tree

From the lectureSuch a multi-level index is a form of search tree. However, insertion and deletion of new index entries is a problem because every level of the index is an ordered file.

Keeping a file sorted while inserting is painful (you must shift things, see Lesson 11). That's exactly the problem the B-tree solves: it leaves some free space in each node so inserts and deletes stay cheap.

Why a B-Tree? (and why not an array?)

We need very fast search on huge data. We also need fast insert, delete and range queries. The B-Tree does all four.

Binary tree vs. B-Tree

No dumb questions
Where does "24 levels" come from?
A binary tree halves the data at each level, so it needs about log₂(10,000,000) ≈ 23.3 → about 24 levels. In the worst case, each level could be a separate page read.

How much can a B-Tree reach?

Example: each page has 500 children (fan-out = 500).

Key pointComparing two numbers in the CPU is extremely fast, like checking your pocket. Reading a page from disk is much, much slower, like walking to a shop. So the best design is the one that makes the fewest page reads, and a wide tree does that.

Why not just a sorted array?

A sorted array is good for searching (binary search, Lesson 03). So why don't databases use it? Because data keeps changing.

Lesson 12

Inside the B-Tree: root, internal, leaf

From the lecture
  • A B-Tree is a multilevel index with a tree structure.
  • Also used to index very large relations when single-level indexes don't fit in main memory.
  • Commercial systems (DB2, ORACLE) implement indexes with B-Trees.
  • The B stands for Balanced tree.
  • A B-tree is usually a 3-level tree: the root, an intermediate level, the leaves.
  • All the leaves are at the same level → balanced tree.
  • The size of each node of the B-tree is equal to a disk block.
  • All nodes have the same format: n keys and n+1 pointers → n key-pointer pairs plus 1 extra pointer.
No dumb questions
What does "balanced" mean?
Every path from the root down to a leaf has the same length. So every search costs the same number of page reads; no unlucky key is buried deeper than the others.
Why n keys and n+1 pointers?
Keys are like fence posts and pointers are the gaps between and around them. 3 keys (23 | 31 | 43) create 4 gaps: below 23, 23–31, 31–43, and 43 or more. Each gap needs a pointer.

Searching for 73: watch the path light up

Root

Where every search starts. There is only one root.

"Go this way."

Internal nodes

Signposts. They guide you to the right range but do not hold the final answer.

"Yes, you are getting closer."

Leaf nodes

The end of the road. They hold the real index entries and the pointers to data.

"Found the key! Here is the row."

B+Tree bonusIn a B+Tree the leaves are linked from left to right. For a range query (e.g. ID from 70 to 90), find 70 once, then just follow the links to the next leaves. No need to climb back up the tree.

B-Tree example from the lecture: the prime numbers 2 to 47

Brain powerUsing the prime tree: how would you get every key from 15 to 30?
Answer: search for 15 → you land in leaf [13 17 19]. Take 17, 19. Follow the link → [23 29], take both. Follow the link → [31 …]: 31 > 30, stop. Result: 17, 19, 23, 29.
Lesson 13

The cost of an index

An index is not magic. You pay for faster reads with more space and slower writes.

① STORAGE

The index needs its own space on disk.
Table 10 GB
Indexes
3 GB
Total = 13 GB (example). The index is extra data.

② INSERT

1 insert = 4 writes (table + 3 indexes).

③ DELETE

The same: the row must be removed from the table + every index. With 3 indexes: 4 writes.

④ UPDATE

It depends on the column.
  • SET Age = 22 (Age has an index) → the table changes and the index changes.
  • SET Name = 'Sara' (no index on Name) → only the table changes.
Smart ruleIndex the columns you often search, join or sort by. Do NOT index everything. Every extra index is one more thing to update.

More indexes = faster reads, slower writes, more storage

Lesson 14

Why INSERT and DELETE cause problems: page splits & fragmentation

When data changes, pages fill up and split. Over time the index becomes messy. This is called fragmentation.

What is a page split?

Two kinds of fragmentation

TYPE A: Empty space

Healthy: 3 pages, all full

Fragmented: same data in 6 half-empty pages

Twice as many pages to read.

TYPE B: Out of order

Disk positions:

The logical order is 1, 2, 3, 4. But the pages sit in different places, so the disk must jump around instead of reading in a straight line.

How a messy index becomes slow

INSERTDELETEINSERTUPDATEDELETEINSERT
Half-empty pages→More pages to read→More I/O→Slower queries

Why INSERT hurts

A full page must split. The new page may be stored far away from its neighbours.

Why DELETE hurts

Deleting rows leaves holes inside pages. Many holes mean many half-empty pages.

Why UPDATE can hurt

If an indexed value changes, its key must move to a new place. That is a delete plus an insert.
Lesson 15

Index maintenance: reorganize or rebuild

An index is not static. It changes with every INSERT, DELETE and UPDATE. So we check it and fix it when needed.

REORGANIZE: a lighter clean-up

ALTER INDEX IX_Students_ID
ON Students
REORGANIZE;
  • Puts leaf pages back in order
  • Packs pages tighter
  • Stays online, can be stopped
  • Good for medium fragmentation

REBUILD: builds a fresh new index

ALTER INDEX IX_Students_ID
ON Students
REBUILD;
  • Removes all fragmentation
  • Uses more CPU, space and time
  • Also refreshes statistics
  • Good for heavy fragmentation

Step 1: measure the fragmentation

-- Step 1: measure the fragmentation
SELECT i.name, ps.avg_fragmentation_in_percent, ps.page_count
FROM sys.dm_db_index_physical_stats(DB_ID(), OBJECT_ID('Students'), NULL, NULL, 'LIMITED') AS ps
JOIN sys.indexes AS i ON ps.object_id = i.object_id AND ps.index_id = i.index_id;
No dumb questions
What does this query return?
For each index on the Students table: its name, its average fragmentation % (avg_fragmentation_in_percent) and its size in pages (page_count). sys.dm_db_index_physical_stats is a built-in SQL Server function that measures index health; sys.indexes holds the index names. 'LIMITED' is the fastest scan mode.
Does every DELETE need a REBUILD?
NO. We measure the index first. Then we decide if maintenance is needed.
Lesson 16

Creating and dropping indexes in SQL

From the lecture Most SQL implementations support the creation and removal of indexes.
  • An index is created by the create index command:
    CREATE INDEX <index-name> ON <relation-name> (<attribute-list>)
  • To remove an index, we use the drop index command:
    DROP INDEX <index-name>
CREATE → make it
ALTER … REORGANIZE / REBUILD → fix it
DROP → delete it
Example from the lectureTo define an index named branch-index on the Account relation with branch-name as the search key: 
CREATE INDEX branch-index ON Account (branch-name);

DROP INDEX branch-index;
Watch it! (real SQL Server) The lecture shows the general textbook form. When you type it in real SQL Server, two details change:
  1. Names with a hyphen must be written in brackets or use an underscore: branch_index, [branch-name].
  2. SQL Server needs to know the table when dropping: DROP INDEX branch_index ON Account;
CREATE INDEX branch_index ON Account (branch_name);
DROP INDEX branch_index ON Account;

-- clustered index: decides the physical row order (only one per table)

-- non-clustered index (the default): a separate sorted structure + pointers
CREATE NONCLUSTERED INDEX IX_Emp_LastName ON Employees (LastName);

-- unique index: no duplicate values allowed
CREATE UNIQUE INDEX IX_Emp_Email ON Employees (Email);

-- composite index: built on multiple columns
CREATE INDEX IX_Emp_Name ON Employees (LastName, FirstName);

-- maintenance (Lesson 15)
ALTER INDEX IX_Emp_LastName ON Employees REORGANIZE;
ALTER INDEX IX_Emp_LastName ON Employees REBUILD;

Side branch: Dense vs Sparse

DENSE: one entry per record. Bigger. Any data order.

SPARSE: one entry per block. Smaller. Data must be sorted on the key.

Side branch: index kinds

Sorted + key → Primary
Sorted + non-key → Clustering
Not sorted → Secondary (dense, many)

Three ideas that make everything click

1 · B-Tree

It reduces the number of disk / page accesses during a search.

2 · Pages

The database reads and writes blocks / pages, not record by record.

3 · Maintenance

INSERT, DELETE and UPDATE change the index. This can cause page splits and fragmentation.

Why not a sorted array?Insert and delete must move too many items.
Why pages?Disks read blocks. One page equals one tree node.
Why is Dense bigger?One entry per record, and records are far more than blocks.

Why maintenance?Changes cause page splits and fragmentation.

Part C · Model answers for the written questions

A good answer covers the points below; wording can differ.

71The objective of query processing is to answer a query effectively and efficiently. Effective means the result is accurate: the right rows, nothing missing, nothing extra. Efficient means a short response time. Indexes mainly improve efficiency: instead of scanning all blocks (up to 10,000,000 rows in the Students example), the DBMS searches a small sorted structure and follows a pointer (about 4 page reads with a B-Tree). A wrongly used index can harm effectiveness: a sparse index on unsorted data can send the search to the wrong block and report "not found" for a key that exists (e.g. searching 30 when the index says 20 → Block 2, but 30 is in Block 1).
72A table is mapped to one or more physical files; each row is mapped to a file record. Records are grouped into fixed-size blocks/pages (8 KB in SQL Server), which are the smallest unit of transfer between disk and memory; a page usually holds several records. The blocking factor bfr = block size ÷ record size (rounded down) tells how many records fit in a block (e.g. 4096 ÷ 100 → 40). To INSERT, DELETE or UPDATE, the DBMS: (1) finds the blocks/pages involved, (2) loads them into memory, (3) performs the operation, (4) saves the result to disk, in the Log Data File (LDF) or Master Data File (MDF). Files can be heap (no order) or sequential (sorted on an ordering field).
73A dense index has one entry for every record (search-key value); a sparse index has one entry per block, so only some keys appear. Dense is bigger because the number of records is much larger than the number of blocks (10,000,000 records at 100 per block → 10,000,000 dense entries vs. 100,000 sparse entries). Sparse only works on data sorted on the search key: the search finds the biggest index key ≤ the target, goes to that block and looks inside. This assumes each block covers one continuous range (e.g. 50–89). If the data isn't sorted, the target may be in another block and the search wrongly says "not found". Dense: bigger, works on any order, can answer "not found" without reading data. Sparse: smaller (more fits in memory), less maintenance overhead, needs sorted data, always reads one block.
74Primary: data file sorted on the search key, which is a key (usually the primary key); entries (key value, block pointer), one per block (block anchor) → sparse; only one per file; usually fits in memory. Clustering: data file sorted on an ordering field that is a non-key (repeats allowed, but not null); entries (value, block pointer), one per distinct value pointing to the first block containing it → usually sparse; one per file, and a file can't have both a primary and a clustering index because it can only be sorted one way. Secondary: any file type, on a field the file is not sorted on (key or non-key, not null); one entry per record → must be dense; a file can have many; less efficient because one key may need several data blocks (more I/O). For a non-key, an extra level of record-pointer blocks is often used.
75A clustered index defines the physical order of the rows (e.g. rows stored by EmployeeID); only one per table. A non-clustered index is a separate structure holding the indexed column(s) plus a pointer to the row in the clustered index (or heap); many are allowed (e.g. on LastName). It is not necessarily built over unsorted values. A primary index is created automatically on the primary key, ensures uniqueness and is often clustered. A secondary index is any index that is not the primary one, an extra lookup path, usually on a non-primary attribute. The difference: "secondary" is a logical idea (is it the primary index or not?), while "non-clustered" is a physical idea (does it decide row order or just store a mapping?). Most secondary indexes are non-clustered because the primary is usually clustered, but not all.
76A multilevel index is an index on an index. It is needed when a single-level index is too large to fit in memory. Because the single-level index is itself an ordered file, we build a primary (sparse) index on it: the original becomes the first-level index, the new one is the second level. We repeat (third, fourth…) until all entries of the top level fit in one disk block. Each level divides the search by the fan-out, so the number of block reads ≈ number of levels + 1. Trade-off: faster search, slower updates. It is a form of search tree, but because every level is an ordered file, insertions and deletions are a problem (entries must be shifted). B-Trees solve this.
77We need fast search, insert, delete and range queries, and the expensive operation is a page read, not a CPU comparison. A binary tree has only 1 key and 2 children per node, so it is tall and thin: about 24 levels for 10,000,000 records, i.e. many page reads. A B-Tree has many keys and children per node (one node = one page), so it is short and wide: 3–4 levels (fan-out 500 → 125,000,000 entries in 3 levels), about 6× fewer steps. A sorted array supports fast binary search, but inserting or deleting requires shifting many items (millions in a big table), and it needs one big continuous block. A B-Tree inserts with a page split (only 2 pages and 1 parent key change), deletes by changing a few pages, and grows page by page. With linked leaves (B+Tree), range queries are fast.
78A B-Tree is a balanced, multilevel tree index (used by DB2 and Oracle). It is usually 3 levels: the root (only one, where every search starts), internal/intermediate nodes (signposts that guide to the right range), and leaves (hold the real index entries and pointers to data rows). All leaves are at the same level (balanced), so every search costs the same. Every node is the size of one disk block and has the same format: n keys and n+1 pointers; pointer Pᵢ leads to values between Kᵢ₋₁ and Kᵢ. A B+Tree links its leaves left to right, so a range query finds the first key once and then follows the links.
79Indexes trade write speed and space for read speed. Storage: each index takes its own disk space (e.g. table 10 GB + indexes 3 GB = 13 GB). INSERT: the row is written to the table and to every index (3 indexes → 4 writes). DELETE: the same, table + every index. UPDATE: depends on the column. If the column is indexed (SET Age = 22 with an index on Age), both the table and that index change; if not (SET Name = 'Sara'), only the table changes. Writes per insert grow with the number of indexes (0→1, 1→2, 3→4, 5→6). Smart rule: index the columns you often search, join or sort by; don't index everything.
80When a page is full and a new key must go into it, the page splits into two pages that are each about half full, and the new page may be far away on disk. Over time INSERTs (splits), DELETEs (holes) and UPDATEs of indexed values (delete + insert) cause fragmentation. Type A, empty space: the same data spread over more half-empty pages (6 instead of 3), so twice as many pages to read. Type B, out of order: the logical page order (1, 2, 3, 4) doesn't match the physical order, so the disk jumps around. Result: more pages → more I/O → slower queries. Maintenance: first measure (sys.dm_db_index_physical_stats). Under 5%: OK. 5–30%: REORGANIZE (lighter, reorders leaf pages, packs them, stays online, can be stopped). Over 30%: REBUILD (fresh index, removes all fragmentation, refreshes statistics, costs more CPU/space/time). Indexes under about 1,000 pages are usually not worth fixing. Not every DELETE needs a rebuild.
