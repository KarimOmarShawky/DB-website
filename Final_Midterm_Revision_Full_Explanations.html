Part 1 · Section A

Indexing: how data is stored and found

Lesson 01

The big picture: why do we need indexes?

Before we talk about indexes, let's see where they live and what problem they solve.

Where does a query go?

When you use an app (a website, a mobile app, a banking program…) and it needs data, it sends a query (a question, usually written in SQL) to the DBMS, the Database Management System. The DBMS is the software that manages the database, for example SQL Server, Oracle or MySQL. The DBMS finds the answer in the database and sends back a result.

No dumb questions
What is a "relation"?
It is the formal (mathematical) name for a table. A relation = a table, a tuple = a row, an attribute = a column. You'll see both sets of words in database courses.
What is "meta data"?
"Data about data." The table holds your actual data (students, orders…). Meta data describes it and helps the DBMS work with it: what tables exist, what indexes exist, statistics about how many rows there are, etc.

What is the problem?

From the lecture Objective: Effectively and efficiently answering a given query.
  • Effective: the accuracy of the query results (is the answer correct?).
  • Efficient: the response time (how fast did the answer come back?).

✔ Effective = correct

You asked for the student with ID 8734291 and you got that student, not someone else, not nothing.

⚡ Efficient = fast

You got the answer in a few milliseconds, not after a minute of waiting.

Indexes are mainly about efficiency: they make the DBMS find the correct answer much faster. (But as you'll see in Lesson 04, a wrongly used index can even break effectiveness!)

Lesson 02

How data lives on disk: files, records & pages

To understand indexes you first need to know how a table is physically stored. Good news: it's simpler than it sounds.

Tables become files, rows become records

From the lecture
  • A database table is mapped to physical file(s).
  • A database row is mapped to file record(s).
  • The smallest unit of data transfer is a block/page.
  • Typically, a block/page contains multiple records.
No dumb questions
Block or page: what's the difference?
For this course, treat them as the same thing: a fixed-size chunk of storage that is read or written in one go. "Block" is the operating-system / disk word, "page" is the database word. In SQL Server, one page = 8 KB.
Why can't the disk just give me one record?
Disks and SSDs physically move data in blocks. Reading one byte costs almost the same as reading the whole block, so the DBMS always reads whole pages.

What happens when you INSERT, DELETE or UPDATE?

1Find the blocks / pages that are involved.
▼
2Load them into memory (RAM).
▼
3Do the operation (in memory).
▼
4Save it to disk: the Log Data File (LDF) or the Master Data File (MDF).

In SQL Server, a database has an .mdf file (the main data file holding tables and indexes) and an .ldf file (the transaction log that records changes).

Blocking factor (bfr)

How many records fit into one block? That number has a name: the blocking factor.

bfr = Block Size ÷ Record SizeRound down: a record can't be cut in half across two blocks (in this simple model).
Example Block size = 4096 bytes, record size = 100 bytes.
bfr = 4096 ÷ 100 = 40.96 → 40 records per block (round down).
If the table has 30,000 records, it needs 30,000 ÷ 40 = 750 blocks (round up here: a partly-filled last block is still a block).
Records per block: round DOWN.
Number of blocks: round UP.

Two ways to organise a file

🗃️ Heap file

An un-organized space where records are kept without any clear order. New records are just dropped wherever there is room, like papers thrown on a pile.

Block 1701090 Block 23010040

Finding a value? You may need to look at every block.

📂 Sequential (ordered) file

Records are stored in an organized order (SEQUENTIAL) based on some field, like neatly labelled folders.

Block 1103040 Block 27090100

The field the file is sorted on is called the ordering field.

Why the database thinks in pages

✗ NOT like this

"Give me byte number 7,834,291."

✔ LIKE this

"Give me the whole PAGE that has it."

① Hardware reads blocks

Disks and SSDs move data in blocks. Reading one byte costs almost the same as reading a whole block.

② One read, many keys

A single 8 KB page can hold hundreds of keys. So one read removes a huge part of the search.

③ Simple mapping

One tree node = one page. Reading, writing and splitting become easy to manage.
Key pointWe don't design an index to look nice in RAM. We design it to reduce the number of page I/O (page reads and writes).
I/O = Input/Output = reading from or writing to disk.
Brain powerComparing two numbers in the CPU is extremely fast, like checking your pocket. Reading a page from disk is much, much slower, like walking to a shop. If you had to find something, would you rather make 4 trips to the shop or 24? That's the whole reason indexes are designed around pages.
Lesson 03

What exactly is an index?

From the lectureIndexing is the principal technique used to efficiently answer a given query.

The book analogy

An index for a database is like the index at the back of a book:

  1. It is smaller than the book.
  2. The words are in sorted order.
  3. If we are looking for a particular topic we first search the index, find the pages where it is discussed, then go to the actual pages in the book.

A book has 500 pages. To find "Photosynthesis" you can read every page, or open the index at the back, see "page 214" and go straight there. A database index does exactly this for rows.

Example from the lecture Table: MovieStar(Name, Address, Gender, Birthdate) 
SELECT * FROM MovieStar WHERE Name = 'Jim Carrey';
If there is no index on Name, all the blocks of the MovieStar relation must be inspected and visited. With an index on Name, the DBMS looks up "Jim Carrey" in the (small, sorted) index and jumps directly to the right block.

The formal definition

From the lecture
  • An index is an auxiliary file structure (an extra, helper file, separate from the data file).
  • Indexes are created on one or more columns of a table.
  • An index is created for specific field(s), usually the field(s) that appear in the WHERE clause of SQL queries.
  • An index speeds up searches, but it slows down other DML operations (INSERT, UPDATE, DELETE).
  • Changes in the data MUST be followed by index change and refreshment.
No dumb questions
What is DML?
Data Manipulation Language: the SQL commands that change data: INSERT, UPDATE, DELETE (and SELECT to read it).
Why does an index slow down INSERT/UPDATE/DELETE?
Because the index is a copy of some of the data, kept in sorted order. Every time the table changes, the index must also be changed so it stays correct. More work per change = slower changes. (Lesson 13 shows exactly how much.)
What does "search key" mean?
The column (or columns) the index is built on: the value you search by. It doesn't have to be the table's primary key; "key" here just means "the thing we look up".

Indexes as access paths

An access path is a route the DBMS can take to reach the data. A full scan is one access path; an index is a much shorter one.

  • The index file usually occupies considerably fewer disk blocks than the data file, because its entries (just key + pointer) are much smaller than full data records.
  • An index is always sorted on the index field(s).
  • A binary search on the index yields a pointer to the file record.
  • Indexes can be DENSE or SPARSE (next lesson!).

Binary search in 30 seconds

Binary search works on sorted data. Look at the middle; if your value is bigger, throw away the left half; if smaller, throw away the right half. Repeat. Each step removes half of the data.

Dense vs. sparse indexes

Both are indexes. The only difference is how many entries they keep.

From the lecture
  1. Dense: one entry in the index file for every record (every search-key value) in the data file.
  2. Sparse (or NON-DENSE): one entry in the index file for each block of the data file, so it has entries for only some of the search values.

More facts about sparse indexes

From the lecture
  • A sparse index contains index records for only some search-key values: some keys in the data file will not have an entry in the index file.
  • Applicable when records are sequentially ordered on the search key (ordered files).
  • Normally keeps only one key per data block.
  • Less space (so more of the index can be kept in memory).
  • Less maintenance overhead for insertions and deletions.

When does sparse work?

A sparse index has no entry for most records. It relies on a promise: "everything between my entry 50 and my entry 90 is inside block 2." That promise is only true if the data is sorted on the search key.

Key pointA sparse index works well when the data file is ordered on the search key. If the data is not ordered, use a dense index (one entry per record).
Watch it!Remember Lesson 01's "effective vs efficient"? A sparse index on unsorted data doesn't just get slower, it gives a wrong result. That's a failure of effectiveness (accuracy), not just efficiency.
Lesson 05

The map of index types

Your lecture lists these types. Get the big map in your head first; the most important ones get their own lessons next.

Single-level indexes

1. Primary index

Automatically created on the primary key; ensures uniqueness.

2. Unique index

Ensures all values in the column(s) are unique (e.g. no two users with the same email).

3. Clustered index

Sorts and stores the data rows physically in order of the key. One per table.

4. Non-clustered index

Stores pointers to the data rather than the actual rows. Multiple allowed.

5. Composite index

Built on multiple columns, e.g. (LastName, FirstName).

6. Bitmap index

Efficient for low-cardinality columns: columns with few distinct values, e.g. gender.

7. Full-text index

Used for searching text fields efficiently (words inside articles, descriptions…).

8. Spatial index

Used for location-based / geospatial queries ("restaurants within 2 km").

9. Hash index

Uses hash tables for very fast equality lookups (WHERE x = 5).

Multi-level indexes

1. B-tree

A balanced, multi-level tree index (Lessons 10–12).

2. B+ tree

A B-tree variant whose leaves are linked together, great for range queries.
Text → Full-text
Map/location → Spatial
Few values → Bitmap
Exact "=" only → Hash
Many columns → Composite
No dumb questions
What is "cardinality"?
The number of distinct values in a column. Gender has low cardinality (few values). National ID number has high cardinality (every value different).
What is a bitmap?
A row of bits (0/1). For a gender column, a bitmap index keeps one bit-string per value, e.g. "Male: 1 0 0 1 1 …" meaning rows 1, 4, 5 are male. Very compact when there are few values.
What is a hash?
A function that turns a value into a "bucket number". Same value → same bucket, so an exact match is found almost instantly. But hashing scrambles order, so it's not good for ranges like "between 100 and 200".
Why only one clustered index per table?
Because rows can't be stored in two different physical orders at the same time, just like a bookshelf can't be sorted by author and by colour at once.
Lesson 06

Primary index

From the lecture
  • An index on a sequential (ordered) file: the index is associated with a data file that is itself sorted on the search key.
  • Usually used when the search key is also the primary key of the relation.
  • Usually, these indexes fit in main memory.
  • An index file record = (field value, block pointer).
  • How many primary indexes can we build for a data file? One primary index per data file.
Brain powerIn this example, is the primary index dense or sparse? (Think before reading the answer below.)

Answer: Sparse. There is one entry per block, not per record. "Abbot, Diane" has no entry of its own; we find her by going to the "Aaron, Ed" block and looking inside.
Key pointPrimary index = sorted data file + ordering field is a key (unique) + entries (key value, block pointer) + one entry per block (sparse) + only one per file.
Number of index entries = number of data blocks.
No dumb questions
Why only one primary index per file?
A primary index needs the data file to be physically sorted on its field. A file can be physically sorted in only one way, so only one such index is possible.
Why does it usually fit in main memory?
It only has one small entry per block. If a block holds 40 records, the index has 40 times fewer entries than the table has rows, and each entry is tiny.
Lesson 07

Clustering index

What if the file is sorted on a field that is not unique, like department number? Then we use a clustering index.

From the lecture
  • For sequential (sorted) data files.
  • Based on the ordering field: not necessarily unique, but must be not null.
  • An index file record = (field value, block pointer).
  • For every distinct ordering-field value → one index record.
Key pointClustering index: sorted file, ordering field is a non-key (repeats allowed, but NOT NULL), one entry per distinct value. It is usually sparse (fewer entries than records).
Watch it!Primary and clustering indexes both need the file physically sorted. A file can be sorted on only one field, so a file has either a primary index or a clustering index, not both.
Lesson 08

Secondary index

The file can only be sorted one way. But we want fast searches on other columns too. Solution: secondary indexes.

From the lecture
  • For any data file type (sorted, unsorted, heap…). The data is not sorted on the indexing field.
  • Secondary indexes facilitate query-answering on any attributes (PK or not, but not null).
  • The indexing field is not necessarily the ordering field.
  • A file can have several secondary indexes. → How many? Many.
  • A secondary index is dense. → It must be dense.
  • More than one data block may be needed for a given search key, so in general more disk I/O to answer queries: secondary indexes are less efficient than primary indexes.

Clustered vs. non-clustered index

These words describe physical storage (how rows sit on disk). They're the words used in SQL Server.

Clustered index

Defines the physical order of the data in the table. Only one per table (rows can't be stored in two different physical orders).

Example: a clustered index on EmployeeID means rows are stored in ascending order of EmployeeID.

Page 1123Page 2456

The table IS the index.

Non-clustered index

A separate structure (like a lookup table) holding the indexed column(s) + a pointer to the actual row in the clustered index (or in the heap, if there is no clustered index). Many allowed per table.

Example: a non-clustered index on LastName creates a sorted list of last names with pointers to the actual employee rows.

It is not necessarily created over unsorted values.

A separate "phone book" pointing to the table.

Primary vs. secondary index (the SQL-world view)

Primary index

Created automatically on the primary key (often clustered by default). Ensures uniqueness and usually defines the row storage order.

Secondary index

Any index that is not the primary index. It can be clustered or non-clustered, depending on implementation. Typically refers to an extra lookup path on a non-primary attribute.
Key difference: secondary vs non-clustered
  • Secondary index is a logical concept → any index besides the primary one (could be clustered or non-clustered).
  • Non-clustered index is a physical storage structure → it doesn't change row order, it just stores a mapping.
In practice (especially in SQL databases): most secondary indexes are non-clustered, because the primary one is usually clustered. But not all secondary indexes are necessarily non-clustered.
Logical question: "Is it the primary one?"
Physical question: "Does it decide row order?"
Lesson 10

Multilevel indexes

An index makes searching the table fast. But what if the index itself becomes huge? Simple: build an index for the index.

From the lecture
  • Used when the index file is too large to fit in memory.
  • Because a single-level index is an ordered file, we can create a primary index to the index itself.
    • The original index file is called the first-level index; the index to the index is called the second-level index.
  • We can repeat the process, creating a third, fourth, …, top level until all entries of the top level fit in one disk block.
  • Result: faster search, but slower updates.

A two-level primary index

Key pointEach level reduces the search by a factor equal to the number of entries per block (called the fan-out). With a fan-out of 500, two levels already reach 500 × 500 = 250,000 blocks.

Multilevel index = a search tree

From the lectureSuch a multi-level index is a form of search tree. However, insertion and deletion of new index entries is a problem because every level of the index is an ordered file.

Keeping a file sorted while inserting is painful (you must shift things, see Lesson 11). That's exactly the problem the B-tree solves: it leaves some free space in each node so inserts and deletes stay cheap.

Lesson 12

Inside the B-Tree: root, internal, leaf

From the lecture
  • A B-Tree is a multilevel index with a tree structure.
  • Also used to index very large relations when single-level indexes don't fit in main memory.
  • Commercial systems (DB2, ORACLE) implement indexes with B-Trees.
  • The B stands for Balanced tree.
  • A B-tree is usually a 3-level tree: the root, an intermediate level, the leaves.
  • All the leaves are at the same level → balanced tree.
  • The size of each node of the B-tree is equal to a disk block.
  • All nodes have the same format: n keys and n+1 pointers → n key-pointer pairs plus 1 extra pointer.
No dumb questions
What does "balanced" mean?
Every path from the root down to a leaf has the same length. So every search costs the same number of page reads; no unlucky key is buried deeper than the others.
Why n keys and n+1 pointers?
Keys are like fence posts and pointers are the gaps between and around them. 3 keys (23 | 31 | 43) create 4 gaps: below 23, 23–31, 31–43, and 43 or more. Each gap needs a pointer.

Searching for 73: watch the path light up

Root

Where every search starts. There is only one root.

"Go this way."

Internal nodes

Signposts. They guide you to the right range but do not hold the final answer.

"Yes, you are getting closer."

Leaf nodes

The end of the road. They hold the real index entries and the pointers to data.

"Found the key! Here is the row."

B+Tree bonusIn a B+Tree the leaves are linked from left to right. For a range query (e.g. ID from 70 to 90), find 70 once, then just follow the links to the next leaves. No need to climb back up the tree.

Lesson 13

The cost of an index

An index is not magic. You pay for faster reads with more space and slower writes.

① STORAGE

The index needs its own space on disk.
Table 10 GB
Indexes
3 GB
Total = 13 GB (example). The index is extra data.

② INSERT

1 insert = 4 writes (table + 3 indexes).

③ DELETE

The same: the row must be removed from the table + every index. With 3 indexes: 4 writes.

④ UPDATE

It depends on the column.
  • SET Age = 22 (Age has an index) → the table changes and the index changes.
  • SET Name = 'Sara' (no index on Name) → only the table changes.

More indexes = faster reads, slower writes, more storage

Lesson 14

Why INSERT and DELETE cause problems: page splits & fragmentation

When data changes, pages fill up and split. Over time the index becomes messy. This is called fragmentation.

What is a page split?

Two kinds of fragmentation

TYPE A: Empty space

Healthy: 3 pages, all full

Fragmented: same data in 6 half-empty pages

Twice as many pages to read.

TYPE B: Out of order

Disk positions:

The logical order is 1, 2, 3, 4. But the pages sit in different places, so the disk must jump around instead of reading in a straight line.

How a messy index becomes slow

INSERTDELETEINSERTUPDATEDELETEINSERT
Half-empty pages→More pages to read→More I/O→Slower queries

Why INSERT hurts

A full page must split. The new page may be stored far away from its neighbours.

Why DELETE hurts

Deleting rows leaves holes inside pages. Many holes mean many half-empty pages.

Why UPDATE can hurt

If an indexed value changes, its key must move to a new place. That is a delete plus an insert.
Lesson 15

Index maintenance: reorganize or rebuild

An index is not static. It changes with every INSERT, DELETE and UPDATE. So we check it and fix it when needed.

REORGANIZE: a lighter clean-up

ALTER INDEX IX_Students_ID
ON Students
REORGANIZE;
  • Puts leaf pages back in order
  • Packs pages tighter

Lesson 18

The big picture: the problem and the vocabulary

Before any algorithm, let's understand what a database is actually being asked to do, and why that is harder than it looks.

The problem in one sentence

From the lecture Problem: efficiently answering a given query.

A user (or an application) sends a query. The DBMS runs query processing and sends back a result. Simple, right? The catch is the word efficiently. A query over a table of millions of rows can be answered in a few milliseconds or in several minutes, depending entirely on how the DBMS decides to do the work.

Four terms from the lecture

From the lecture
  • The DBMS has algorithms to implement relational algebra expressions.
  • SQL is a different kind of high-level language: you specify what is wanted, not how it is obtained.
  • Optimization is not necessarily "optimal", but reasonably efficient. Techniques: heuristic rules + cost estimation.
  • Query optimization = the process of choosing a suitable execution strategy for processing a query.

1. "What, not how": declarative language

Imagine ordering food in a restaurant. You say "one grilled chicken, no onions" (what you want). You do not tell the chef which pan to use, in which order to chop things, or how hot the stove should be (how). SQL works the same way:

SELECT Lname FROM EMPLOYEE WHERE Dno = 5;   -- WHAT: last names of department 5

Nothing in this statement says "scan the file" or "use the index on Dno". Choosing that is the DBMS's job. Relational algebra, in contrast, is procedural: an expression like σ Dno=5 (EMPLOYEE) is already an ordered recipe of operations. Query processing is the translation from the "what" language to a "how" recipe.

2. "Algorithms to implement relational algebra"

Every relational algebra operator (select σ, project π, join ⋈, union ∪, …) must be implemented by a real piece of code that reads blocks from disk. For one operator there are usually several algorithms (selection alone has six in this lecture). Which one is best depends on what indexes exist and how the file is stored.

3. "Not necessarily optimal"

Think of a GPS app. Finding the mathematically best route among billions of possibilities would take so long that you would have arrived by car already. So the GPS settles for a very good route, fast. A DBMS does the same: the number of possible execution plans grows quickly, and the time spent searching for the perfect plan must not exceed the time saved. So the goal is reasonably efficient, not perfect.

4. The two techniques

Heuristic rules

Rules of thumb that almost always help, e.g. "do selections early, so later operations see fewer rows". They cost nothing to apply because no numbers are needed.

Cost estimation

Use statistics (number of rows, blocks, available indexes) to estimate how many block reads each candidate plan needs, then pick the cheapest.
No dumb questions
If SQL doesn't say how, who decides?
The query optimizer, a component inside the DBMS. You will meet it in Lesson 02.
Can two different plans give the same answer?
Yes, always. Plans differ only in speed, never in the answer. That is exactly what makes optimization legal: the DBMS may pick any equivalent plan.
Why should I care as a student or developer?
Because the plan the DBMS can build depends on what you gave it: indexes, sensible conditions, sorted files. This lecture shows which structure unlocks which algorithm.
Brain powerA table has 1,000,000 rows and you ask for the one row with Ssn = '123'. Name two very different ways the DBMS could find it. Which needs more disk reads, and why can't SQL tell the DBMS which to use?
SQL = WHAT
Optimizer = HOW
Lesson 19

The life of a query: from text to result

A SQL string is just text. Before a single block is read from disk, it passes through a small assembly line.

From the lecture Query evaluation process (typical steps when processing a high-level query): Query in a high-level language → scanning, parsing and validating → intermediate form of query → query optimizer → execution plan → query code generator → code to execute the query → runtime database processor → result of query.
The code can be executed directly (interpreted mode) or stored and executed later whenever needed (compiled mode).

Stage by stage

  1. Scanning breaks the text into tokens: SELECT, Lname, FROM, EMPLOYEE… This is like splitting a sentence into words.
  2. Parsing checks the grammar: is the order of keywords right? SELECT FROM WHERE EMPLOYEE fails here.
  3. Validating checks the meaning against the catalog (meta data): does table EMPLOYEE exist? Does it have a column Lname? Are types compatible?
  4. Intermediate form: the validated query is stored as an internal structure, normally a query tree (Lesson 04) or an equivalent graph.
  5. Query optimizer: uses heuristic rules + cost estimates to choose an execution plan: which algorithm to use for each operator.
  6. Query code generator: converts the plan into code the DBMS engine can run.
  7. Runtime database processor: runs that code, reads blocks, and produces the result.

Interpreted or compiled?

Interpreted mode

The generated code is executed directly, right now, once. Typical of an ad-hoc query you just typed into a console.

Compiled mode

The code is stored and run whenever needed, again and again, without redoing steps 1–6. Typical of a query embedded in an application (a stored procedure or prepared statement).
Example A banking app runs SELECT Balance FROM Account WHERE AccNo = ? a million times a day. Optimizing it once and storing the plan (compiled) saves a million repetitions of parsing and optimizing. A one-off report you type once is simply interpreted.
Watch it!Errors are caught at different stages. A misspelled keyword (SELCT) is a parsing error. A correct statement that names a table that doesn't exist (FROM EMPLOYE) is a validation error. Neither ever reaches the optimizer.

No. Same figure, taken from different editions of the textbook. Only the caption number changes.

Query trees and how they are executed

An algebra expression becomes a picture: a tree. Reading the tree bottom-up tells you exactly what happens, in what order.

From the lectureQuery tree corresponds to a relational algebra expression.
  • Input relations (tables) → leaf nodes
  • Relational algebra operations → internal nodes
  • Execution (evaluation): starts at the leaf nodes; internal nodes are replaced by the result relation; ends at the root node.

How to run a tree: bottom-up replacement

  1. Find a node whose children are all leaves (already-existing tables). Here: node ① σ (child: PROJECT).
  2. Execute it; replace the node by its result. Now ① is a small temporary relation of 4 projects.
  3. Move up: node ② now has two available inputs (the 4 projects and DEPARTMENT). Execute, replace.
  4. Same for ③ with EMPLOYEE. Finally the root π keeps five columns. That output is the answer.

Query blocks and nested queries

Real SQL often has a query inside a query. The optimizer can't optimize a whole nested monster at once, so it cuts it into pieces.

From the lectureA query block contains a single SELECT-FROM-WHERE expression (along with ORDER BY, GROUP BY and HAVING, if any).

The lecture's example

SELECT LNAME, FNAME
FROM   EMPLOYEE
WHERE  SALARY > ( SELECT MAX(SALARY)
                 FROM   EMPLOYEE
                 WHERE  DNO = 5 );

In English: "List the employees who earn more than the best-paid employee of department 5." This text contains two query blocks, because there are two SELECT-FROM-WHERE units.

Example Department 5 salaries: 30,000 · 38,000 · 25,000 · 40,000. The inner block returns C = 40,000. The outer block then keeps every employee in any department with Salary > 40,000. If three employees earn 43,000, 55,000 and 40,000, the answer lists the first two; the one earning exactly 40,000 is not included because the condition is strictly ">".

Why does the optimizer split queries into blocks?

  • A block is the unit of optimization. The optimizer chooses an execution plan for each block separately. Each block is small enough that its plan can be searched sensibly.
  • The blocks are linked: results of an inner block are fed to the outer one, as above.
Watch it!Count blocks by counting SELECT … FROM … WHERE units, not by counting tables or keywords. The example uses the table EMPLOYEE twice, yet it is still exactly two blocks. And a plain query with GROUP BY and HAVING is still one block.
No dumb questions
Is the inner block always run once?
Here yes: it doesn't mention anything from the outer query, so its answer C never changes. (Nested queries that do refer to the outer row are called correlated and are costlier; the optimizer tries to rewrite them. That topic goes beyond this lecture.)
Why the funny F symbol?
ℱ is the algebra operator for aggregates (MAX, MIN, SUM, COUNT, AVG). Plain σ and π cannot compute a maximum.

Why block reads?

Reading a block from disk takes milliseconds; the CPU can compare millions of values in the same time. So a plan that reads 12 blocks beats one that reads 3,000, even if the 12-block plan does more computing. You already know the unit of transfer is a block (page), holding several records.

How the buffer changes the picture

The DBMS keeps a buffer pool in main memory: a set of slots, each able to hold one disk block. If a block you need is already in a slot, reading it costs nothing from disk. Consequences:

  • Index blocks (small, used by every query) tend to stay in the buffer, so the top index levels are practically free. The lecture says it directly later: index blocks are small and often already in memory.

  • More buffer slots → fewer disk reads → lower real cost than the formulas predict. The formulas are therefore worst-case-ish estimates.

Does the DBMS really know r, b and x?
Yes: they are statistics kept in the catalog (meta data). They are what the optimizer plugs into cost formulas.

S1 linear search and S2 binary search

The two algorithms that need no index at all. One always works; the other works only if the file is sorted.

S1: linear search (brute force)

From the lectureSimple condition algorithms. Comparison type: equality and non-equality. Comparison attribute: any (without any access structure). How: scan the data file, block by block, looking for records satisfying the comparison. aka: linear search / brute force.
S1 works on a heap file, on any field, for equality and non-equality alike. Any file, any condition, and always the slowest.

Linear search is what you do when you look for a name in an unsorted pile of paper forms: pick up form 1, check, put down, pick up form 2… The DBMS reads block 1, tests every record in it against the condition, keeps the matches, discards the rest, then reads block 2, and so on to the end of the file.

S2: binary search

From the lectureComparison type: equality. Comparison attribute: ordering key without an index. How: navigate the data file using binary search to locate the data block. Jump to the middle block, compare, discard half. Repeat. Requires the file to be physically sorted on the search field, so it helps for exactly one field.

It's the "guess the number" game: a friend thinks of a number from 1 to 100; you ask "higher or lower than 50?" and halve the range each time. A sorted file lets the DBMS do the same with blocks: look at the middle block; because the file is sorted, the target must be either entirely before or entirely after it, so half the file is eliminated with one read.

From the lectureComparison type: non-equality. Comparison attribute: key with primary index. Example: σ empno>100 (EMPLOYEE). How: navigate the index to locate the data block with the corresponding equality condition, then retrieve preceding or subsequent records.

Conjunctive conditions (AND)

Real queries rarely have a single condition. With AND, you only need to find a way to satisfy one of them cheaply; the rest can be checked afterwards.

Our running query: σ DNO=5 AND SALARY>30000 AND Gender='F' (EMPLOYEE). A record qualifies only if all three hold. Logic gives us a gift: any record in the answer must satisfy DNO=5. So we can use a fast path for that one condition and throw everything else away afterwards.

Strategy B: a composite index

From the lectureWhen: a group of comparison attributes with a composite index appears in equality comparisons. Example: DNO=5 AND SALARY>30000 AND Gender=F; assume a composite index on (DNO, GENDER). How: use the composite index to retrieve satisfying records; apply the remaining comparisons.

Watch it!The composite index here helps because both indexed columns are compared with equality. It can't serve a condition on Salary at all (not part of the index), and column order matters: an index on (Dno, Gender) can't efficiently answer "Gender='F'" alone.

From the lectureWhy this wins: index blocks are small and often already in memory; data blocks are large and on disk. Intersecting the pointer sets first means you only ever touch data blocks that satisfy every condition. Requires record pointers, not block pointers.

Lesson 31

Disjunctive conditions (OR)

With OR, logic works against us: a record qualifies if it satisfies any one condition, so you must find all of them.

From the lectureDisjunctive conditions (OR):
  • Every disjunct must be evaluated: a record satisfying any one of them belongs in the result.
  • So: run a simple-condition algorithm on each disjunct, union the results, and remove duplicates.
  • If even one disjunct has no access path, the whole query falls back to a linear scan.
  • AND lets you pick the best index. OR forces you to use them all, or none.

Why can't we just use one index?

Take Dno=5 OR Salary>30000. An index on Dno finds the Dno=5 people. But a department-7 employee earning 50,000 also qualifies, and no Dno index will ever find them. Each disjunct contributes records the others miss, so every disjunct must be searched.

Example σ Dno=5 OR Ssn='123' (EMPLOYEE). Dno=5 returns 4 records (r12–r15); Ssn='123' returns r14, which happens to live in department 5 as well. Union with duplicates would list r14 twice. After duplicate removal, the answer has 4 records. In a relation, a record is either in the result or not; it can't appear twice.
Now change it: Dno=5 OR Salary>30000 where Salary has no index. Disjunct 2 has no access path, so you'd have to scan the whole file anyway to evaluate it, and while scanning you might as well test both conditions at once. Result: one S1 pass; the Dno index is never used.

From the lectureThe CARTESIAN PRODUCT of relations R and S includes all possible combinations of records from R and S. The attributes of the result include all attributes of R and S. Lesson 35

Where we are: the operator families and the bottlenecks

Before any algorithm, a map: which operators are cheap, which are expensive, and why joins and selections get all the attention.

From the lectureRelational algebra operators can be classified into three groups [selection, projection, grouping, duplicate elimination, set operations, Cartesian product, join]:
  • Tuple-at-a-time unary operators: selection and projection. No need to bring the entire relation into memory at one time.
  • Full-relation unary operators: duplicate elimination and grouping. Require seeing all or most of the tuples in memory at once.
  • Full-relation binary operators: union, intersection, difference, join and Cartesian product. Require seeing the tuples of both relations in memory.

Why does this classification matter? Because memory is the scarce resource of query processing. An operator that handles one tuple and forgets it can work with a single buffer, however large the table. An operator that must remember many tuples (to spot a duplicate, to build a group, to match a join partner) needs more memory, and when memory is short it must go back to the disk more often.

From the lectureQuery optimization — what? Finding the best way to execute a SELECT query; finding the fastest way; finding the way with the least amount of disk access; finding the way with the smallest number of block reads.

The slide asks why. Selection is a bottleneck because it is the first thing that touches the raw tables, and a table can be huge: every extra block read on a big table is paid thousands of times. 1Look at the condition: simple, conjunctive (AND) or disjunctive (OR)?
↓
2Look at the comparison: equality or non-equality?
↓
3Look at the access path: none, ordered file, or an index?
↓
4Pick the algorithm whose estimated block count is smallest

How big is a join result? Join selectivity

Before costing a join we need to know how many blocks of output it writes.

Join cost has two parts: the cost of reading the input files, and the cost of writing the result. The second part needs an estimate of how big the result is.

Why the result size matters

From the lectureWhat is the problem about join? The result should be stored, and other operations may be done on it ("intermediate results"). The resulting file is stored to disk. R ⋈ S ⋈ T ≡ (R ⋈ S) → store result as RS, then RS ⋈ T. How to estimate the result?

Join selectivity (js)

js = |R ⋈A=B S| / |R × S|0 ≤ js ≤ 1 · the fraction of the Cartesian product that survives the join condition

No join condition

That is a Cartesian product: every pair survives, so js = 1.

No matching tuples

Nothing survives, so js = 0.

From js to blocks

result records = js × |R| × |S|
result blocks = ⌈ (js × |R| × |S|) / bfrRS ⌉bfrRS = blocking factor of the result file (records per block)
ExampleEMPLOYEE ⋈Dno=Dnumber DEPARTMENT. |EMPLOYEE| = 10,000, |DEPARTMENT| = 125, js = 1/125, bfrED = 4.
result records = (1/125) × 10,000 × 125 = 10,000. That makes sense: every employee belongs to exactly one department, so the result has one record per employee.
result blocks = 10,000 / 4 = 2,500.
No dumb questions
Where does js = 1/125 come from?
DEPARTMENT's join attribute (Dnumber) is a key with 125 values, and every EMPLOYEE record matches exactly one. In a key–foreign key join, js = 1 / |relation holding the key|.
Is the result blocking factor the same as the inputs'?
No. Result records are wider (they carry the attributes of both), so fewer fit per block. That is why bfrED = 4 here while EMPLOYEE has bfr = 5 and DEPARTMENT has bfr = 10.
Key pointEvery join algorithm pays the same output term, (js × |R| × |S|) / bfrRS. It does not depend on the algorithm. Only the reading part differs, which is why the lecture compares algorithms on their reading cost.

Buffers and the choice of outer relation

The same join can cost 19 blocks or 17 blocks depending on which file you put outside. Here is why.

The lecture poses a question on two successive slides: "Which is better, R ⋈A=B S or S ⋈B=A R? Calculate the number of blocks that are read. It depends on who is the smaller and bigger relation." Same join, same answer, different cost, just by swapping which file is outer.

Counting block reads

Take R with bR = 7 blocks, S with bS = 3 blocks. The buffer lets us hold 2 blocks of the outer relation at a time.

bR + ⌈ bR / Buffers ⌉ × bSR in the outer loop · "Buffers" = how many outer blocks fit in memory at a time

The ruleRule: put the SMALLER relation in the outer loop. The outer relation is read once either way (7 or 3); what changes is the number of chunks, and each chunk costs one full scan of the inner relation. Fewer blocks outside → fewer chunks → fewer scans of the big file.

From "Buffers" to nB − 2

From the lectureAssume the memory buffer is nB blocks: cost = bR + ⌈bR/(nB − 2)⌉ × bS + (js × |R| × |S|)/bfrRS — "Why?"

The slide leaves the why as a question. Here is the answer. Of the nB memory blocks you cannot give all of them to the outer relation:

  • 1 block to read the current block of the inner relation S;
  • 1 block as the output buffer where result records are built before being written;
  • the remaining nB − 2 blocks hold the outer chunk.

So in the first example, "we consider 2 blocks to read from outer R" means nB − 2 = 2 (nB = 4). That is why the quiz question "bR = 7, bS = 3, nB = 4" has the answer 19.

Sort-merge join (J3)

Two sorted files, two pointers, one pass: the cheapest join there is, if the files are already ordered.

From the lectureSort-merge join (J3). When: R is ordered by A and S is ordered by B. Cost: bR + bS + ((js × |R| × |S|) / bfrRS).

If both files are sorted on their join attributes, matching records are neighbours in both files, so two pointers walking down the files once will meet every match. Each file is read exactly once.

The algorithm

sort the tuples in R on attribute A;   -- skip if already sorted
sort the tuples in S on attribute B;
i ← 1; j ← 1;                          -- n = |R|, m = |S|
while (i ≤ n) and (j ≤ m) do {
  if      R(i)[A] > S(j)[B]  then j ← j + 1
  else if R(i)[A] < S(j)[B]  then i ← i + 1
  else {                                   -- R(i)[A] = S(j)[B]: a match
     output <R(i), S(j)> to T;
     l ← j + 1;                           -- other S tuples matching R(i)
     while (l ≤ m) and (R(i)[A] = S(l)[B]) { output <R(i), S(l)> to T; l ← l + 1 }
     k ← i + 1;                           -- other R tuples matching S(j)
     while (k ≤ n) and (R(k)[A] = S(j)[B]) { output <R(k), S(j)> to T; k ← k + 1 }
     i ← k; j ← l                         -- jump past the whole group
  }
}

Lesson 47

The evaluation problem and what optimization means

SQL tells the DBMS what we want; it is the optimizer that decides how to get it cheaply.

From the lectureQuery evaluation. Problem: an SQL query is declarative — it does not specify a query execution plan. A relational algebra expression is procedural — there is an associated query execution plan. Solution: convert the SQL query to an equivalent relational algebra expression and evaluate it using the associated query execution plan. But which equivalent expression is best?

SQL says what you want. Relational algebra says which operations, in which order. Converting SQL to algebra therefore gives the DBMS a recipe, but a query almost always has many equivalent recipes that return the same rows at wildly different costs. Choosing between them is the optimizer's job.

Where the optimizer sits

1Parsing and translation: the query becomes a relational-algebra expression
↓
2Optimization: the optimizer picks an execution plan, using statistics about the data
↓
3Evaluation: the evaluation engine runs the plan against the data and produces the query output
From the lectureQuery optimization = re-writing a query to produce an equivalent, but a better query. Initial query tree → optimization (rewriting) → final query tree. Equivalent: produces the same result set. Better: costs less (disk access, computation, memory usage, communication).
WordMeaningConsequence

the best way to execute a SELECT query
the fastest way to execute it

No dumb questions
If the answer is the same, why does the plan matter?
Because cost is not the answer, it is the route. Joining two tables of 10,000 and 30,000 rows and then filtering can mean processing 300,000,000 pairs; filtering first may leave a few hundred rows to join.
Does the optimizer change my SQL?
No. It changes the plan (the algebra tree and the algorithms), never the result.
Lesson 48

Two techniques: heuristics and cost estimation

The two tools of the optimizer, and why a real DBMS needs both.

From the lectureTwo main techniques for query optimization. Heuristic rules: rules for ordering the operations in query optimization. To transform a relational expression into another equivalent expression we need transformation rules that preserve equivalence. Cost estimation: it estimates the cost of different execution strategies and chooses the execution plan with the lowest execution cost.

Heuristic rules

Rewrite the query tree into an equivalent one that is usually cheaper. No statistics needed: the rules hold whatever the data looks like.

Output: a better tree.

Cost estimation

Price several plans using catalog statistics, then pick the cheapest. Needs numbers, and the numbers are estimates.

Output: a chosen algorithm for each operation.

Real systems use both. Heuristics shrink the search space cheaply; cost estimation then makes the final choices among what is left.

Lesson 49

Heuristics and the main heuristic

A rule of thumb that nearly always pays: shrink the data as soon as you can.

From the lectureHeuristics: techniques that don't have proofs; reached by trial-and-error or common sense. Heuristic optimization: applying transformations that produce a better query tree; a transformation must produce an equivalent tree.

A heuristic is a rule of thumb. Nobody proves that "filter early" is always optimal; it simply works almost every time, and costs nothing to apply. (The transformation must be provably equivalent; it is the claim that it makes things better that is only a heuristic.)

From the lectureThe main heuristic is to apply first the operations that reduce the size of intermediate results. Apply the operations that reduce the unary relation [tuple based]: e.g. apply SELECT and PROJECT operations before applying the JOIN or other binary operations. Note: perform select operations as early as possible to reduce the number of tuples, and perform project operations as early as possible to reduce the number of attributes. (This is done by moving select and project operations as far down the tree as possible.) The task of heuristic optimization of query trees is to find a final query tree that is efficient to execute.

Why early selection and projection help

  • σ early removes rows: fewer tuples flow into every later operator.
  • π early removes columns: each record is narrower, so more records fit in a block and fewer blocks are read and written.
Watch it!Only the attributes still needed may be projected away. Pushing a projection below a join must keep the join attributes and anything needed above (the final attribute list). Dropping a join column too early would make the join impossible.
Brain powerA join needs 10,000 × 30,000 comparisons. If a selection first cuts the second table to 300 rows, by what factor does the join work shrink?

Heuristic guidelines and the Aquarius query tree

One query, five rewrites, and a tree that does thousands of times less work.

From the lectureHeuristic optimization guidelines: apply σ and π as early as possible (reduce the relation size: number of rows, absolute size); apply the most restrictive σ earlier; apply the most restrictive ⋈ earlier; if possible, avoid ×.

The Aquarius query, stage by stage

SELECT lname
FROM   employee, works_on, project
WHERE  (pname = 'Aquarius') and (pnumber = pno) and (essn = ssn) and (bdate > '1957-12-31');

"Last names of employees born after 1957 who work on the project called Aquarius."

Stage (a) · Initial query tree: direct translation

With illustrative sizes EMPLOYEE = 10,000, WORKS_ON = 30,000, PROJECT = 100: EMPLOYEE × WORKS_ON already has 300,000,000 tuples, and × PROJECT makes 30,000,000,000. Every one of them is built, then almost all thrown away.

Stage (b) · Break σ up and move each piece down (rules 1, 2, 6)

π Lname( σ Pnumber=Pno( σ Essn=Ssn( σ Bdate>'1957-12-31'(EMPLOYEE) × WORKS_ON ) × σ Pname='Aquarius'(PROJECT) ) )

Each single-table condition now sits right on its table: the birth-date filter on EMPLOYEE, the project-name filter on PROJECT. The two join conditions (Essn=Ssn, Pnumber=Pno) involve two tables, so they can only sink as far as the × that brings those tables together.

Stage (c) · Most restrictive σ first (rule 9, 5: re-arrange the leaves)

π Lname( σ Essn=Ssn( σ Pnumber=Pno( σ Pname='Aquarius'(PROJECT) × WORKS_ON ) × σ Bdate>'1957-12-31'(EMPLOYEE) ) )

Pname = 'Aquarius' keeps probably one PROJECT row out of many, far more restrictive than Bdate > …. So PROJECT is combined with WORKS_ON first, producing a small intermediate result (the assignments to that one project). EMPLOYEE is joined last.

Lesson 53

The six heuristic optimization steps and pipelining

The lecture's procedure: six steps that turn any initial tree into an efficient final tree.

From the lectureHeuristic optimization steps:
  1. Break up any select operations with conjunctive conditions into a cascade of select operations.
  2. Move each select operation as far down the query tree as is permitted by the attributes involved in the select condition.
  3. Re-arrange the leaf nodes of the tree so that the leaf node relations with the most restrictive select operations are executed first in the query tree representation.
  4. Combine a Cartesian product operation with a subsequent select operation in the tree into a join operation.
  5. Break down and move lists of projection attributes down the tree as far as possible by creating new project operations as needed.
  6. Identify sub-trees that represent groups of operations that can be executed by a single algorithm (pipelining).

Step 6: pipelining

Without pipelining each operator would write its full result to disk, and the next one would read it back. Pipelining passes each result record straight to the next operator as it is produced, so the intermediate result never touches the disk. A chain such as π(σ(EMPLOYEE)) can run as one algorithm: read a record, test it, drop unneeded columns, pass it on.

No dumb questions
Why must step 1 come before step 2?
A single σ with four AND-ed conditions cannot go anywhere as one block: its conditions refer to different tables. Splitting it lets each piece sink independently.
Why step 4 before step 5?
Projection lists depend on which attributes the joins need. Joins must therefore exist before we know which columns to keep.
Key pointThe order of the steps is part of the answer. Cascade → push σ → order leaves → ×+σ→⋈ → push π → pipeline. Exams often ask you to list or apply them in order.

Cost-based optimization: what cost means

From "usually better" to "estimated to be cheapest": the unit of cost is the block access.

Heuristics produce a better tree but cannot say which algorithm to use for each operation, or which of two reasonable plans is cheaper. For that the optimizer needs numbers.

From the lectureCost-based optimization: pick the best plan by comparing estimated costs.

Components of cost

From the lectureCost estimation: I/O block accesses, only! Cost = disk access: number of blocks read, number of blocks written [we ignore it in many cases]. Cost of reading = finding the first block + reading all blocks with matching records.

Why only I/O?

One disk block read costs thousands of times more than one in-memory comparison, so I/O dominates. Counting only block accesses keeps the estimate simple enough to compute for every candidate plan.

Memory buffers

From the lectureSeveral algorithms can reduce disk I/O by using extra buffer space. The amount of real memory available to buffer depends on other concurrent queries and OS processes, known only during execution. We often use worst-case estimates, assuming only the minimum amount of memory needed for the operation is available. Required data may be buffer-resident already, avoiding disk I/O, but that is hard to take into account for cost estimation.
No dumb questions
So estimates may be too pessimistic?
Yes, deliberately. The real run may find blocks already in memory, but the optimizer cannot count on it; assuming the worst gives a safe comparison between plans.
Are writes always ignored?
Not always. The slide says writes are ignored "in many cases". For joins, the lecture does include the cost of writing the result blocks.

Histograms

From the lectureHistogram: the number of values/tuples in each of a number of intervals. Widely used.
