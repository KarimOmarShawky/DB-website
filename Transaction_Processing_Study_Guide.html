Lesson 01

What is a transaction?

A transaction is how a database turns a real-world event, like moving money, into one safe unit of work.

From the lecture
  • A transaction is a sequence of database actions considered as a unit of work.
  • The actions are read R(X), write W(X), commit and abort.
  • It reflects a single real-world transition: in the real world it either happened completely or not at all.
  • Examples: transfer money between accounts, purchase a group of products, register for a class.

Example: transferring LE1000

Move LE1000 from Account #1025 to Account #224. In database terms that is six small steps that must stay together:

StepActionAccount #1025Account #224
1read(#1025)1,000 → in memory
2#1025 := #1025 − 1000after: 0
3write(#1025)0 saved
4read(#224)500 → in memory
5#224 := #224 + 1000after: 1,500
6write(#224) then COMMIT01,500

Balances are invented to make the arithmetic visible.

What goes wrongIf the system crashes after step 3 but before step 6, LE1000 has left #1025 and never arrived in #224. Money has vanished. The transaction idea says: either all six steps happen, or none of them is kept.

Transactions in SQL

  • In ad-hoc SQL the default is each statement = one transaction.
  • In a program, several statements are grouped between a begin and an end (slide labels: Begin Transaction, T-SQL DML, End Transaction).
START TRANSACTION
  UPDATE Bank SET amount = amount - 100 WHERE name = 'Bob'
  UPDATE Bank SET amount = amount + 100 WHERE name = 'Joe'
COMMIT
ExamplePurchasing three products: reduce stock for each of the three and create the order. If the third stock update fails, the first two must not stay. The group is one transaction.
Brain powerIs a single UPDATE statement a transaction?

Answer: Yes, by default each SQL statement is its own transaction.
Lesson 02

Read and write: how data really moves

Transactions only ever do two things to data: read it and write it. Both go through a memory buffer.

From the lecture
  • The database is a set of data items. An item can be one record or one disk block.
  • read_item(X) reads database item X into the program variable X.
  • write_item(X) writes the value of program variable X into database item X.

read_item(X): three steps

  1. Find the address of the disk block that contains X.
  2. Copy that block into a buffer in main memory (if it is not already in some buffer).
  3. Copy X from the buffer to the program variable X.

write_item(X): four steps

  1. Find the block that contains X.
  2. Copy the block into a memory buffer (if not already there).
  3. Copy X from the program variable into its correct place in the buffer.
  4. Store the updated block back to disk, either immediately or at some later point in time.

Example: X = 8 becomes X = 10

MomentDiskMemory bufferProgram variable X
Start8——
After read_item(X)888
Program computes X := X + 28810
After write_item(X) steps 1–381010
After step 4 (flush)101010
Watch outStep 4 may happen later. Between steps 3 and 4 the new value exists only in memory. That gap is why the system needs a log and a recovery manager (Lessons 3 and 4).
Brain powerAfter step 3 of write_item(X) but before step 4, where is the new value of X?

Answer: Only in the memory buffer and program variable; disk still holds the old value.
No dumb questions
Why does the DBMS not always write to disk immediately?
The lecture only says the block is stored immediately or at some later time. The practical point for this course: until it is stored, the new value is not on disk.
Lesson 03

The ACID properties

Four promises a DBMS makes about every transaction.

PropertyLecture meaningBank-transfer example
AtomicityPerformed in its entirety or not at all. Two outcomes: it commits (all changes made) or it aborts (no changes made).Both the debit and the credit happen, or neither.
Consistency preservationA correct execution takes the database from one consistent state to another. Integrity constraints always hold (unique account number, stock cannot be negative).Total money in the two accounts is unchanged.
IsolationUpdates are not visible to others until commit. The effect is as if each transaction ran alone.Another transaction cannot see the half-done transfer.
DurabilityOnce committed, changes must never be lost, even after crashes or power failure. Means: write data to disk.After “transfer done”, a power cut cannot undo it.

Which property is broken?

ScenarioProperty at risk
Crash after the debit, before the creditAtomicity
Balance goes negative although the rule forbids itConsistency
Two customers both buy the last itemIsolation
Confirmed order disappears after a power cutDurability
Another user sees a half-finished transferIsolation

Who makes each one true?

  • Atomicity: the DBMS undoes partial transactions. It keeps a log of all writes; the recovery manager is the component responsible.
  • Consistency: the programmer must write a transaction that takes a consistent state to a consistent state, and the system makes sure it is atomic.
  • Durability: the effect must persist after the transaction, after the program ends, and despite crashes. It means writing data to disk.
Example: atomicity in actionT writes X (80 → 75) and then the system crashes before T commits. On restart the recovery manager reads the log, sees T never committed, and undoes the write: X returns to 80.
Common confusionAtomicity (all-or-nothing) and Isolation (not seeing others’ half-done work) are different. A lost update is an isolation failure: each transaction was atomic, but they interfered.
Brain powerA crash happens after COMMIT but before the data reached disk. Which property is under threat?

Answer: Durability. Committed changes must survive, which is why the system relies on its log.
No dumb questions
Does durability mean data can never change again?
No. It means committed changes are not lost by failures. Later transactions may update them.
Lesson 04

Transaction states and failures

At every moment a transaction is in exactly one state. The system tracks them so it can recover.

The five states

StateMeaning
ActiveRunning; performs read and write operations
Partially committedIts last operation (end transaction) has executed; the commit is not yet complete
CommittedSuccessfully finished; all changes are permanent
FailedNormal execution cannot continue (abort)
TerminatedLeft the system

The state diagram

Transitions (the state diagram)

Three example journeys

  • Success: Active → Partially committed → Committed → Terminated.
  • Error while running (for example stock would go negative): Active → Failed → Terminated.
  • Failure at the last moment: Active → Partially committed → Failed → Terminated.

Why recovery is needed: types of failure

  • A computer failure (system crash)
  • A transaction or system error
  • A local error or exception condition detected by the transaction
  • Concurrency control enforcement
  • Disk failure
  • Physical problems and catastrophes
Key pointCommitted and Failed are the two ways a transaction ends: COMMIT = every change is reflected in the database; ABORT = none of the changes is. Transactions are motivated by two DBMS properties: recoverability and concurrency.
Brain powerCan a transaction go from Committed back to Failed?

Answer: No. The diagram has no abort arrow out of Committed. Once committed, the changes are permanent (durability).
No dumb questions
What is the difference between Partially committed and Committed?
Partially committed: the last operation has run but the commit is not complete, so a failure can still abort it. Committed: it is finished and safe.
Lesson 05

Why run transactions concurrently?

Real systems have many users at once. The challenge is letting them share data without corrupting it.

Single-user vs multi-user

Single-userMulti-user
ExamplePhonebookBanks, flight reservation, hospitals, stock market
Concern hereNot our concernOur main concern

Interleaving vs parallel processing

  • Parallel processing: several CPUs really execute operations at the same instant.
  • Interleaving (our concern): at any instant only the operations of one transaction execute; the system does a context switch to run operations of another transaction.

Why not just run one after another?

Serial-only execution gives low throughput, long response time and poor resource utilization (CPU, disks). Concurrency improves waiting time, response time, resource utilization and efficiency.

ExampleT1 is waiting for a disk read. A serial system leaves the CPU idle. An interleaved system switches to T2 and uses the CPU meanwhile. Both finish sooner overall.
Price of concurrencyInterleaving can produce wrong results. The next lesson shows the four classic problems.
Brain powerName one benefit of interleaving over strictly serial execution.

Answer: Better throughput and resource use: while T1 waits for disk, the CPU works on T2.
No dumb questions
Does interleaving always give wrong answers?
No. Only some interleavings are unsafe, and the next lessons show how to recognise them.
Lesson 06

The four concurrency problems

Every example uses the lecture’s numbers: X = 80, Y = 20, N = 5, M = 4. T1 transfers N from X to Y; T2 does something else with X.

1. Lost update

T1: read X; X := X − N; write X. T2: read X; X := X + M; write X.

TimeT1T2X in database
1read_item(X) → 8080
2read_item(X) → 8080
3X := 80 − 5 = 75
4X := 80 + 4 = 84
5write_item(X)75
6write_item(X)84

Result: X = 84. Correct (either serial order): 80 − 5 + 4 = 79. T1’s update was overwritten, i.e. lost.

2. Dirty read (temporary update)

T1 updates X, T2 reads it, then T1 aborts.

TimeT1T2X
1read X → 80; X := 75; write X75
2read X → 75 (dirty)
3X := 75 + 4 = 79; write X; COMMIT79
4ABORT (X should go back to 80)?

Result: T2 used a value that never officially existed. Without T1, X should be 80 + 4 = 84, but the database holds 79.

3. Unrepeatable read

T2 reads X twice and gets different values.

TimeT1T2
1read X → 80
2read X; X := 75; write X
3read X → 75

4. Incorrect summary

Database: X = 80, Y = 20, A = 10. T2 computes sum = A + X + Y while T1 moves 5 from X to Y.

TimeT1T2Sum
1sum := 0; read A; sum := 1010
2read X; X := 75; write X
3read X → 75; sum := 8585
4read Y → 20; sum := 105105
5read Y; Y := 25; write Y

Result: 105. Correct: 10 + 80 + 20 = 10 + 75 + 25 = 110. T1’s effect was only partially considered (the slide’s caption names the mix as X-before / Y-after, while its figure shows X after and Y before; either mix is wrong).

ProblemMemory trickTypical cause
Lost updateOverwritten by a stale valueBoth read before either writes
Dirty readRead uncommitted data that later abortsRead between write and abort
Unrepeatable readSame item, two reads, two valuesAnother transaction writes in between
Incorrect summaryAggregate sees half of an updateSum overlaps a running update
Brain powerWhy does the lost update end at 84 and not 79?

Answer: Both transactions computed from the same starting value 80. The later write (84) replaces the earlier one (75) instead of building on it.
No dumb questions
Is a dirty read the same as a lost update?
No. A dirty read reads data that may be rolled back. A lost update overwrites another transaction’s write.
Do these problems happen in serial execution?
No. Serial schedules always ensure consistency; the problems come from unsafe interleaving.
Lesson 07

Schedules and conflicting operations

A schedule is the order in which operations of several transactions actually run. Conflicts are what make some orders dangerous.

From the lecture
  • A schedule S of n transactions T1…Tn is an ordering of execution of the operations of those transactions.
  • A serial schedule runs T1 completely, then T2: it ensures consistency, so there is no risk.

Notation

r = read, w = write, c = commit, a = abort. In r1(X): r is the operation, 1 is the transaction ID and X is the data item.

Sc: r1(X); r2(X); w1(X); r1(Y); w2(X); c2; w1(Y); c1;

Conflicting operations

RuleTwo operations conflict iff (1) they belong to different transactions, (2) they access the same data item, and (3) at least one is a write.
PairConflict?Why
r1(X), r2(X)NoBoth reads
r1(X), w2(X)Yes (read-write)Different transactions, same item, one write
w1(X), r2(X)Yes (write-read)Same
w1(X), w2(X)Yes (write-write)Same
r1(X), w2(Y)NoDifferent items
r1(X), w1(X)NoSame transaction

Worked example: find the conflicts in Sc

  • Item X is touched by both transactions: r2(X) with w1(X) (read-write).
  • r1(X) with w2(X) (read-write).
  • w1(X) with w2(X) (write-write).
  • Item Y is used only by T1, so it has no conflicts.

Three conflicting pairs. Because Sc is not serial and has conflicts, it carries a risk of inconsistency.

Is a schedule proper?

A proper (complete) schedule contains all operations of all transactions and keeps each transaction’s own order. With T1 = r1(X), w1(X), r1(Y), w1(Y) and T2 = r2(X), w2(X):

ScheduleProper?Reason
r1(X); w1(X); r1(Y); w1(Y); r2(X); w2(X)YesSerial, all operations in order
r1(X); w1(X); r2(X); r1(Y); w1(Y); w2(X)YesT1 and T2 keep their own order
r1(X); w1(X); r2(X); w1(Y); r1(Y); w2(X)Now1(Y) appears before r1(Y), breaking T1’s order

More practice: count the conflicting pairs

ScheduleConflicting pairsCount
r1(X); w2(X); w1(Y); r2(Y)r1(X) – w2(X), w1(Y) – r2(Y)2
r1(X); r2(X); r1(Y); r2(Y)none0
w1(X); w2(X); w1(Y); w2(Y)w1(X) – w2(X), w1(Y) – w2(Y)2
r1(X); w2(Y); w1(X); r2(Y)none0

Brain powerWhy does r1(X); r2(X); r1(Y); r2(Y) have zero conflicts even though both transactions use both items?

Answer: Every operation is a read. A conflict needs at least one write.

Step 0: is it a proper schedule?

Before classifying any schedule, check that it is proper. Exam choices often hide an improper schedule among the options, and an improper schedule is never the right answer.

What to checkHow an improper schedule looksExample (T1 = r1(X); w1(X); c1)
Every operation present, exactly onceAn operation is missing or repeatedr1(X); c1; (w1(X) missing)
Each transaction keeps its own orderTwo operations of the same transaction are swappedw1(X); r1(X); c1;
Commit/abort is the last operationA transaction acts after it has committedr1(X); c1; w1(X);
Quick methodFor each transaction, read only its operations from the schedule, left to right, and compare with the transaction as given. If they differ in any way, the schedule is improper.
Lesson 08

Recoverability: recoverable, cascadeless, strict

From the recoverability perspective there are three types of schedules, each stricter than the last.

Why it matters

If T1 writes X, T2 reads X and then T1 aborts, T2 has used dirty data. Can the system still repair things? That is the recoverability question.

1. Recoverable

DefinitionNo transaction T commits until all transactions that wrote an item T read have committed. So T2 must wait for T1 to commit first.
Test
  • Find the write-read conflicts.
  • Find the order in which the transactions terminate.
  • If the transaction that wrote did not terminate first, the schedule is not recoverable; otherwise it is recoverable.

2. Cascadeless (avoids cascading abort)

DefinitionTransactions read only items written by committed transactions. T1 must commit (or abort) before T2 reads X.

Cascading rollback: an uncommitted transaction is forced to roll back because it read an item written by a failed transaction. Example: r1(X); w1(X); r2(X); a1; a2; T2 must abort because it read data that is no longer valid.

Test
  • Find the write-read conflicts.
  • If the writer terminates before the read takes place, the schedule is cascadeless; otherwise it is not.

3. Strict

DefinitionTransactions read and write only items written by committed/aborted transactions. T1 must terminate before T2 reads or writes X.
Test
  • Find the write-read and write-write conflicts.
  • If the first writer terminates before the other operation on that item, the schedule is strict; otherwise it is not.

Venn relationship

Strict ⊂ Cascadeless ⊂ Recoverable ⊂ all schedules. So every strict schedule is cascadeless and recoverable, and every cascadeless schedule is recoverable. The reverse is false.

ScheduleRecoverableCascadelessStrict
w1(X); c1; r2(X); w2(X); c2YesYesYes
w1(X); w2(X); c1; c2YesYesNo
w1(X); r2(X); c1; c2YesNoNo
w1(X); r2(X); c2; c1NoNoNo

ScheduleVerdictReasoning

…w2(X); c1; w1(Y); c2InvalidT1 performs w1(Y) after it has already committed, so this is not a proper schedule.
r1(X); r2(X); w1(X); r1(Y); w1(Y); c1; w2(X); c2StrictT1 terminates before T2 writes X.

Worked exam example (Midterm 2023)

S: R1(x); R3(x); W1(z); W1(x); R3(z); R1(y); C1; W3(y); R2(y); W3(x); C3; R2(x); C2;
  • Write-read conflicts: W1(z)→R3(z); W3(y)→R2(y); W3(x)→R2(x).
  • Recoverable? Writers T1, T3, T3 commit before their readers T3, T2, T2 do (C1 < C3 < C2). Yes.
  • Cascadeless? R3(z) happens before C1. No.
  • Strict? The same read of z before C1 breaks it. No.

Answer: Recoverable, not cascadeless, not strict (this matches the lecturer’s key).

Common mistakes
  • Checking only the order of commits and forgetting that cascadeless is about when the read happens.
  • Forgetting write-write conflicts when testing for strict.
  • Declaring “not recoverable” when the writer commits first: then it is recoverable.

Brain powerIs w1(X); r2(X); c1; c2 recoverable? Cascadeless?

Recoverable: yes (T1 commits before T2). Cascadeless: no, because r2(X) happens before c1.
No dumb questions
Why is every cascadeless schedule also recoverable?
Cascadeless means every read sees only committed data, so the writer has already committed before any reader commits. That is exactly the recoverable condition.
Why is strict stricter than cascadeless?
Strict also restricts writes: nobody may overwrite an item until its last writer has terminated.

How to answer “Which schedule is strict / cascadeless / recoverable?”

  • Eliminate improper schedules first. Check each transaction’s operations against its definition.
  • For the proper ones, list the write-read (and, for strict, write-write) conflicts.
  • Check where each writer’s commit falls: before the later operation (strict/cascadeless) or before the reader’s commit (recoverable).
  • Pick the one choice that meets the stated property.

Worked example

T1: r1(X); w1(X); r1(Y); w1(Y); c1; T2: r2(X); w2(X); c2; Which schedule is strict?

Common mistakes
  • Classifying an improper schedule and picking it because it “looks” strict.
  • Forgetting that a strict schedule is also cascadeless and recoverable, so on a question that asks only for “recoverable”, check whether more than one choice qualifies and read the stem carefully.
  • Counting only commits and ignoring where the read happens.

Part D · Model answers

A good answer covers the points below; wording can differ.

62A transaction is a sequence of database actions treated as one unit of work; actions are read, write, commit and abort. The transfer reads #1025, subtracts 1000, writes it, reads #224, adds 1000, writes it and commits. If a crash happens after the first write, the money left #1025 but never reached #224, so either all steps happen or none is kept.
63Atomicity: debit and credit both happen or neither; the recovery manager undoes partial work using the log. Consistency: constraints such as non-negative balances hold before and after; the programmer writes consistent transactions and the system guarantees atomicity. Isolation: others do not see the half-finished transfer. Durability: after commit the transfer survives crashes because data is written to disk.
64States: Active, Partially committed, Committed, Failed, Terminated. (a) Active → Partially committed → Committed → Terminated. (b) Active → Partially committed → Failed → Terminated. Abort is possible from Active and from Partially committed.
65read: find block, copy to buffer if needed, copy X to the program variable. write: find block, copy to buffer, copy X from program variable into the buffer, then store the block to disk immediately or later. Until the block is stored, the new value exists only in memory, so a crash can lose it unless the log and recovery manager can redo or undo it.
66Parallel processing runs operations at the same instant on several processors. Interleaving runs one operation at a time and context-switches between transactions; this is the lecture’s concern.
