Lesson 01

The evaluation problem and what optimization means

SQL tells the DBMS what we want; it is the optimizer that decides how to get it cheaply.

From the lectureQuery evaluation. Problem: an SQL query is declarative — it does not specify a query execution plan. A relational algebra expression is procedural — there is an associated query execution plan. Solution: convert the SQL query to an equivalent relational algebra expression and evaluate it using the associated query execution plan. But which equivalent expression is best?

SQL says what you want. Relational algebra says which operations, in which order. Converting SQL to algebra therefore gives the DBMS a recipe, but a query almost always has many equivalent recipes that return the same rows at wildly different costs. Choosing between them is the optimizer's job.

Where the optimizer sits

1Parsing and translation: the query becomes a relational-algebra expression
↓
2Optimization: the optimizer picks an execution plan, using statistics about the data
↓
3Evaluation: the evaluation engine runs the plan against the data and produces the query output
From the lectureQuery optimization = re-writing a query to produce an equivalent, but a better query. Initial query tree → optimization (rewriting) → final query tree. Equivalent: produces the same result set. Better: costs less (disk access, computation, memory usage, communication).
WordMeaningConsequence
Equivalentproduces exactly the same result setEvery transformation must be provably safe: the 12 rules of Lesson 4
Bettercosts less: disk access, computation, memory, communicationIn practice disk access (block reads) dominates everything else

Three ways of saying the same thing

the best way to execute a SELECT query
the fastest way to execute it
the way with the fewest disk accesses (the one that matters in practice)
No dumb questions
If the answer is the same, why does the plan matter?
Because cost is not the answer, it is the route. Joining two tables of 10,000 and 30,000 rows and then filtering can mean processing 300,000,000 pairs; filtering first may leave a few hundred rows to join.
Does the optimizer change my SQL?
No. It changes the plan (the algebra tree and the algorithms), never the result.
Lesson 02

Two techniques: heuristics and cost estimation

The two tools of the optimizer, and why a real DBMS needs both.

From the lectureTwo main techniques for query optimization. Heuristic rules: rules for ordering the operations in query optimization. To transform a relational expression into another equivalent expression we need transformation rules that preserve equivalence. Cost estimation: it estimates the cost of different execution strategies and chooses the execution plan with the lowest execution cost.

Heuristic rules

Rewrite the query tree into an equivalent one that is usually cheaper. No statistics needed: the rules hold whatever the data looks like.

Output: a better tree.

Cost estimation

Price several plans using catalog statistics, then pick the cheapest. Needs numbers, and the numbers are estimates.

Output: a chosen algorithm for each operation.

Real systems use both. Heuristics shrink the search space cheaply; cost estimation then makes the final choices among what is left.

Lesson 03

Heuristics and the main heuristic

A rule of thumb that nearly always pays: shrink the data as soon as you can.

From the lectureHeuristics: techniques that don't have proofs; reached by trial-and-error or common sense. Heuristic optimization: applying transformations that produce a better query tree; a transformation must produce an equivalent tree.

A heuristic is a rule of thumb. Nobody proves that "filter early" is always optimal; it simply works almost every time, and costs nothing to apply. (The transformation must be provably equivalent; it is the claim that it makes things better that is only a heuristic.)

From the lectureThe main heuristic is to apply first the operations that reduce the size of intermediate results. Apply the operations that reduce the unary relation [tuple based]: e.g. apply SELECT and PROJECT operations before applying the JOIN or other binary operations. Note: perform select operations as early as possible to reduce the number of tuples, and perform project operations as early as possible to reduce the number of attributes. (This is done by moving select and project operations as far down the tree as possible.) The task of heuristic optimization of query trees is to find a final query tree that is efficient to execute.

Why early selection and projection help

  • σ early removes rows: fewer tuples flow into every later operator.
  • π early removes columns: each record is narrower, so more records fit in a block and fewer blocks are read and written.
Watch it!Only the attributes still needed may be projected away. Pushing a projection below a join must keep the join attributes and anything needed above (the final attribute list). Dropping a join column too early would make the join impossible.
Brain powerA join needs 10,000 × 30,000 comparisons. If a selection first cuts the second table to 300 rows, by what factor does the join work shrink?
Lesson 04

The 12 relational algebra transformation rules

The only moves the optimizer is allowed to make: each one preserves the result.

To rewrite a tree safely we need rules that preserve equivalence. The lecture gives twelve. Learn them in groups: rules about σ (1, 2, 4, 6, 10), about π (3, 4, 7, 11), about ⋈ and × (5, 6, 7, 9, 12), and about set operations (8, 9, 10, 11).

ExampleRule 1 then 2 (cascade, commute).

Rule 6 (σ below ⋈).
σSalary>300 AND Pname='X'(EMPLOYEE ⋈ PROJECT): Salary belongs to EMPLOYEE and Pname to PROJECT, so the second form applies: (σSalary>300(EMPLOYEE)) ⋈ (σPname='X'(PROJECT)).

σDno=Dnumber(EMPLOYEE × DEPARTMENT) = EMPLOYEE ⋈Dno=Dnumber DEPARTMENT.
Watch it!Three rules have fine print. Rule 4 needs the selection attributes to be in the projection list; rule 6 needs the condition to mention only the relation it is pushed into; rule 7 must keep the join attributes. And never commute “−” (rule 8) or associate it (rule 9 lists only ⋈, ×, ∪, ∩).
No dumb questions
Does rule 10 work for set difference too?
The lecture states it for a generic set operator θ, which includes ∪, ∩ and −: σc(R − S) = σc(R) − σc(S).
Why is rule 5 important if the result is the same?
Because of cost: the nested-loop join is cheaper with the smaller relation outer, and rule 5 says swapping them is legal.
σ and π: push DOWN
× + σ: make ⋈
“−” never commutes
Lesson 05

Remember: SQL → algebra → three equivalent forms

The lecture's smallest example of rewriting, before the big one.

From the lectureRemember: SELECT Name, age FROM Employee, Dept WHERE Depno = Depnumber AND age < 30. In relational algebra: πName,age(σDepno=Depnumber AND age<30(Employee × Dept)).

The standard translation maps the three SQL clauses to three operators: SELECT → π, FROM → × (Cartesian product of all listed tables), WHERE → σ.

Three equivalent expressions

FormExpressionWhat changed
1 · Direct translationπName,age(σDepno=Depnumber ∧ age<30(Employee × Dept))Cartesian product of both tables, then filtering. The most expensive form.
2 · Rule 12πName,age(σage<30(Employee ⋈Depno=Depnumber Dept))σ + × became ⋈, leaving only the age condition above the join.
3 · Rules 6 and 5πName,age(Dept ⋈Depno=Depnumber (σage<30(Employee)))σ pushed below the join onto Employee (rule 6); inputs swapped (rule 5). The best of the three.

The lecture shows (2) with an arrow because it is already a big improvement; (3) goes further. All three return the same rows.

Lesson 06

Heuristic guidelines and the Aquarius query tree

One query, five rewrites, and a tree that does thousands of times less work.

From the lectureHeuristic optimization guidelines: apply σ and π as early as possible (reduce the relation size: number of rows, absolute size); apply the most restrictive σ earlier; apply the most restrictive ⋈ earlier; if possible, avoid ×.
GuidelineWhy
Apply σ and π as early as possibleFewer rows (σ) and narrower rows (π) for every later operator
Apply the most restrictive σ earlierThe condition that removes the most rows shrinks the data the most
Apply the most restrictive ⋈ earlierThe join with the smallest result keeps intermediate results small
If possible, avoid ×A Cartesian product has |R| × |S| tuples; a join has only the matching ones

The Aquarius query, stage by stage

SELECT lname
FROM   employee, works_on, project
WHERE  (pname = 'Aquarius') and (pnumber = pno) and (essn = ssn) and (bdate > '1957-12-31');

"Last names of employees born after 1957 who work on the project called Aquarius."

Stage (a) · Initial query tree: direct translation

With illustrative sizes EMPLOYEE = 10,000, WORKS_ON = 30,000, PROJECT = 100: EMPLOYEE × WORKS_ON already has 300,000,000 tuples, and × PROJECT makes 30,000,000,000. Every one of them is built, then almost all thrown away.

Stage (b) · Break σ up and move each piece down (rules 1, 2, 6)

π Lname( σ Pnumber=Pno( σ Essn=Ssn( σ Bdate>'1957-12-31'(EMPLOYEE) × WORKS_ON ) × σ Pname='Aquarius'(PROJECT) ) )

Each single-table condition now sits right on its table: the birth-date filter on EMPLOYEE, the project-name filter on PROJECT. The two join conditions (Essn=Ssn, Pnumber=Pno) involve two tables, so they can only sink as far as the × that brings those tables together.

Stage (c) · Most restrictive σ first (rule 9, 5: re-arrange the leaves)

π Lname( σ Essn=Ssn( σ Pnumber=Pno( σ Pname='Aquarius'(PROJECT) × WORKS_ON ) × σ Bdate>'1957-12-31'(EMPLOYEE) ) )

Pname = 'Aquarius' keeps probably one PROJECT row out of many, far more restrictive than Bdate > …. So PROJECT is combined with WORKS_ON first, producing a small intermediate result (the assignments to that one project). EMPLOYEE is joined last.

Stage (d) · Replace × and σ with ⋈ (rule 12)

π Lname( ( σ Pname='Aquarius'(PROJECT) ⋈ Pnumber=Pno WORKS_ON ) ⋈ Essn=Ssn σ Bdate>'1957-12-31'(EMPLOYEE) )

No Cartesian product remains. A join on an equality condition can use the join algorithms of the previous lecture.

Stage (e) · Push π down (rules 3, 7)

TableColumns keptWhy exactly these
PROJECTPnumberneeded for the join Pnumber = Pno; nothing else is used above
WORKS_ONEssn, PnoPno for the first join, Essn for the second
EMPLOYEESsn, LnameSsn for the join, Lname for the final answer
after join 1Essnonly Essn is needed to join with EMPLOYEE
ExampleIllustrative effect. σPname leaves 1 project; its join with WORKS_ON yields about 30,000 / 100 = 300 assignments; EMPLOYEE is cut to about 4,000; the last join processes 300 × 4,000 possible pairs through a join algorithm instead of producing 30 billion tuples. The answer is identical.
Watch it!The "most restrictive" choice needs knowledge of the data. The heuristic says "most restrictive first", but deciding that Pname = 'Aquarius' beats Bdate > … relies on knowing how many rows each condition keeps, which is a statistic. This is where heuristic optimization starts to lean on cost estimation.
Lesson 07

The six heuristic optimization steps and pipelining

The lecture's procedure: six steps that turn any initial tree into an efficient final tree.

From the lectureHeuristic optimization steps:
  1. Break up any select operations with conjunctive conditions into a cascade of select operations.
  2. Move each select operation as far down the query tree as is permitted by the attributes involved in the select condition.
  3. Re-arrange the leaf nodes of the tree so that the leaf node relations with the most restrictive select operations are executed first in the query tree representation.
  4. Combine a Cartesian product operation with a subsequent select operation in the tree into a join operation.
  5. Break down and move lists of projection attributes down the tree as far as possible by creating new project operations as needed.
  6. Identify sub-trees that represent groups of operations that can be executed by a single algorithm (pipelining).
StepActionRules usedIn the Aquarius example
1Cascade the conjunctive σ1One σ with four AND-ed conditions becomes four σ nodes
2Push each σ down2, 4, 6, 10Bdate σ onto EMPLOYEE, Pname σ onto PROJECT; join conditions stop at their ×
3Re-order the leaves, most restrictive σ first5, 9PROJECT with σ Pname is combined with WORKS_ON before EMPLOYEE
4× followed by σ → ⋈12Both Cartesian products become joins
5Push π down3, 4, 7, 11π Pnumber, π Essn,Pno, π Ssn,Lname below the joins
6Group pipelinable sub-trees—e.g. σ and π over one table can run in a single pass

Step 6: pipelining

Without pipelining each operator would write its full result to disk, and the next one would read it back. Pipelining passes each result record straight to the next operator as it is produced, so the intermediate result never touches the disk. A chain such as π(σ(EMPLOYEE)) can run as one algorithm: read a record, test it, drop unneeded columns, pass it on.

MaterializedPipelined
Intermediate resultswritten to disk, read backpassed record-by-record in memory
Disk costextra writes + readsnone for the intermediate result
Memorylittlea buffer per operator in the pipeline
No dumb questions
Why must step 1 come before step 2?
A single σ with four AND-ed conditions cannot go anywhere as one block: its conditions refer to different tables. Splitting it lets each piece sink independently.
Why step 4 before step 5?
Projection lists depend on which attributes the joins need. Joins must therefore exist before we know which columns to keep.
Key pointThe order of the steps is part of the answer. Cascade → push σ → order leaves → ×+σ→⋈ → push π → pipeline. Exams often ask you to list or apply them in order.
Lesson 08

Cost-based optimization: what cost means

From "usually better" to "estimated to be cheapest": the unit of cost is the block access.

Heuristics produce a better tree but cannot say which algorithm to use for each operation, or which of two reasonable plans is cheaper. For that the optimizer needs numbers.

From the lectureCost-based optimization: pick the best plan by comparing estimated costs.

Components of cost

ComponentMeasured inExample
I/Oblocksblocks read from and written to disk
StorageMB / GBspace for intermediate results
CPUoperationscomparisons while scanning, sorting, merging
RAMbuffersmemory blocks available to the operation
COMMdata transferredbytes sent over the network (distributed databases)
From the lectureCost estimation: I/O block accesses, only! Cost = disk access: number of blocks read, number of blocks written [we ignore it in many cases]. Cost of reading = finding the first block + reading all blocks with matching records.

Why only I/O?

One disk block read costs thousands of times more than one in-memory comparison, so I/O dominates. Counting only block accesses keeps the estimate simple enough to compute for every candidate plan.

Memory buffers

From the lectureSeveral algorithms can reduce disk I/O by using extra buffer space. The amount of real memory available to buffer depends on other concurrent queries and OS processes, known only during execution. We often use worst-case estimates, assuming only the minimum amount of memory needed for the operation is available. Required data may be buffer-resident already, avoiding disk I/O, but that is hard to take into account for cost estimation.
No dumb questions
So estimates may be too pessimistic?
Yes, deliberately. The real run may find blocks already in memory, but the optimizer cannot count on it; assuming the worst gives a safe comparison between plans.
Are writes always ignored?
Not always. The slide says writes are ignored "in many cases". For joins, the lecture does include the cost of writing the result blocks.

From the lectureSelection cardinality (s) of attribute A of relation r: the average number of records that satisfy equality on A. S = sl × r.

Histograms

From the lectureHistogram: the number of values/tuples in each of a number of intervals. Widely used.

The simple formula sl = 1/d assumes every value is equally frequent. Real data rarely is: in the histogram the interval 18–22 holds far more tuples than the interval under 11. A histogram lets the optimizer estimate a condition such as age BETWEEN 18 AND 22 from the actual frequencies, so its selectivity estimate is much closer to reality.

Watch it!Statistics go stale. Catalog values are updated periodically, not on every insert. After a large load of data, estimates can be badly wrong until the statistics are refreshed, and a cost-based optimizer will happily choose a bad plan from bad numbers.
Lesson 10

S1 linear search and S2 binary search

The two algorithms that need no index at all.

From the lectureσ cost estimation — the algorithms: S1 linear search · S2 binary search · S3a primary index · S3b hashing · S4 ordering index with non-equality · S5 clustering index · S6 secondary index (B-tree).

Each algorithm applies to a specific access path. The hashing algorithm S3b is struck out on the slides: it is not part of this course.

S1 · Linear search (heap file)

From the lectureScan the data file, block by block, looking for records satisfying the comparison. Relation total size = b blocks, stored continuously. Worst case: cost = b. Best case: cost = 1. Average: b/2.

Works for any condition on any field with no structure at all. The example: 9 records, bfr = 2, so b = 5, an unordered file:

BlockRecords (ID: Name)
11:XYZ · 2:IOD
23:DSA · 4:ASD
35:FKL · 6:LOP
47:ABC · 8:XAS
59:OPX
Name = 'XYZ': found in block 1, cost 1 (best case).
Name = 'OPX': found in block 5, cost b = 5 (worst case).
Average over all keys: b/2 = 2.5.

On a non-key attribute, more matches may exist later, so the scan must continue to the end: cost = b.

S2 · Binary search (ordered file)

From the lectureNavigate the data file using binary search to locate the data block. The relation is sorted. cost(S2) = ⌈log2 b⌉ + (⌈s/bfr⌉ − 1). Log2b is the cost to locate the first block; ⌈s/bfr⌉ is the number of blocks that contain records satisfying the selection. Equality on key: Log2b. Equality on non-key: Log2b + (⌈s/bfr⌉ − 1).

Lesson 11

S3a, S4, S5 and S6: the index algorithms

Four ways to use an index, each with its own cost formula.

S3a · Primary index (equality on the key)

From the lectureNavigate the index to locate the index record with the comparison value. Cost = x + 1 (x index levels, plus one data block).
ExampleA two-level primary index (x = 2) on an ordered file; query Key = '35': read the top-level block, the first-level block, then the one data block: 2 + 1 = 3 blocks.

S4 · Ordering index with non-equality

From the lectureNavigate the index to locate the data block with the corresponding equality condition, then retrieve preceding or subsequent records. Cost (rough) = x + b/2.

For Key > 35 or Key < 35 on an ordered file, use the index to jump to the boundary and read the blocks on one side. On average about half the file qualifies, hence b/2.

S5 · Clustering index

From the lectureNavigate the index to locate the first data block satisfying the condition and then retrieve subsequent blocks. Cost = x + ⌈s/bfr⌉.
ExampleClustering index on Dept_number, x = 1, bfr = 4, b = 9. Query Value = '6' with s = 5 records. The matching records are contiguous, so they occupy ⌈5/4⌉ = 2 blocks. Cost = 1 + 2 = 3.

S6 · Secondary index (B-tree)

From the lectureNavigate the index to locate the index record with the comparison value. Index on key: x + 1. Index on non-key: x + 1 + s ("Why? Think and answer"). Non-equality comparison: x + (bi1/2) + (r/2).

Why x + 1 + s for a non-key?

A non-key value occurs s times, and a secondary index does not keep equal records together: they can be in any blocks. So: x blocks to descend the index, 1 block of record pointers, and then up to s data-block reads, one per matching record in the worst case (the lecture's picture of deptnumber 3 scattered across five data blocks). Compare this with the clustering index, where the s records sit together in ⌈s/bfr⌉ blocks.

Why x + bi1/2 + r/2 for a non-equality?

A range condition qualifies about half the entries on average: so half of the first-level index blocks (bi1/2) are read, and about half the records (r/2) are fetched, each potentially from its own block because the file is not ordered on this attribute. That can be enormous.

Summary, key ideas & dictionary

The whole lecture on a page.

Heuristic optimization on one page

  • Goal: an equivalent tree that reduces intermediate results; no statistics needed.
  • Move down: σ and π. Convert: σ + × → ⋈. Avoid: ×. First: the most restrictive σ and ⋈.
  • Steps: cascade σ → push σ → re-order leaves → ×+σ→⋈ → push π → pipeline.
  • Rules: 12, including: ∪ and ∩ commute but − does not; ⋈, ×, ∪, ∩ associate; π keeps join attributes.

Cost-based optimization on one page

  • Unit of cost: block accesses (I/O only), usually worst-case memory.
  • Statistics: r, R, b, bfr, d, sl, s = sl × r, x, bi1, histograms.
  • Compute, don't assume: an index can lose to a linear scan.

Part C · Written (model answers)

46SQL specifies what result is wanted, not a plan; relational algebra is procedural and has an execution plan, but a query has many equivalent algebra expressions. The optimizer chooses among them. Equivalent means the same result set; better means a lower cost (disk access, computation, memory, communication), mainly the number of block accesses. The optimizer changes the plan, never the answer.
47Main heuristic: apply first the operations that reduce the size of intermediate results. σ removes tuples and π removes attributes, so doing them before a join gives the join smaller, narrower inputs. Example: EMPLOYEE × DEPT then σ age<30 builds all pairs first; σage<30(EMPLOYEE) ⋈ DEPT joins only the young employees. The result is the same, the work much smaller. Projections must keep the join attributes.
48(1) Break conjunctive selects into a cascade (rule 1). (2) Move each select as far down as its attributes allow (rules 2, 4, 6, 10). (3) Re-arrange the leaves so those with the most restrictive selects come first (rules 5, 9). (4) Combine × and a following σ into ⋈ (rule 12). (5) Push π lists down by creating new projections (rules 3, 4, 7, 11). (6) Identify sub-trees that can run as one pipelined algorithm.
49A disk block access costs far more than in-memory work, so I/O dominates, and counting blocks is simple enough to do for every candidate plan. Cost estimation must be far cheaper than running the query (jelly-bean analogy), so it uses catalog statistics (r, b, bfr, d, sl, x, bi1) to estimate. A histogram records the number of tuples per interval, correcting the uniformity assumption sl = 1/d when values are unevenly distributed.
50Key: x index levels plus one data block (one match). Non-key: x levels, one pointer block, then up to s data blocks, because matching records are scattered. Range: about half the first-level index blocks and half the records, each possibly in a different block. When many records qualify (large s or a range, e.g. Dno>5: 5,004 vs 2,000, or Gender: 5,002 vs 2,000) the scattered fetches exceed one sequential scan, so linear search wins.
