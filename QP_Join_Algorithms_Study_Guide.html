Lesson 01

Where we are: the operator families and the bottlenecks

Before any algorithm, a map: which operators are cheap, which are expensive, and why joins and selections get all the attention.

From the lectureRelational algebra operators can be classified into three groups [selection, projection, grouping, duplicate elimination, set operations, Cartesian product, join]:
  • Tuple-at-a-time unary operators: selection and projection. No need to bring the entire relation into memory at one time.
  • Full-relation unary operators: duplicate elimination and grouping. Require seeing all or most of the tuples in memory at once.
  • Full-relation binary operators: union, intersection, difference, join and Cartesian product. Require seeing the tuples of both relations in memory.

Why does this classification matter? Because memory is the scarce resource of query processing. An operator that handles one tuple and forgets it can work with a single buffer, however large the table. An operator that must remember many tuples (to spot a duplicate, to build a group, to match a join partner) needs more memory, and when memory is short it must go back to the disk more often.

FamilyOperatorsMemory needTypical trick
Tuple-at-a-time unaryσ select, π project (without DISTINCT)One input bufferStream blocks through; test each record and forget it
Full-relation unaryduplicate elimination, GROUP BY, aggregatesMost of the relationSort first, then one pass over neighbours
Full-relation binary∪ ∩ − ⋈ ×Both relationsSort both, or index one, or chunk one into memory

Query optimization, restated

From the lectureQuery optimization — what? Finding the best way to execute a SELECT query; finding the fastest way; finding the way with the least amount of disk access; finding the way with the smallest number of block reads.
Bottlenecks of a query [selections, projections, joins, …]: selections (σ) and joins (⋈). Why?

The slide asks why. Selection is a bottleneck because it is the first thing that touches the raw tables, and a table can be huge: every extra block read on a big table is paid thousands of times. Join is a bottleneck because it must relate two files to each other, and the naive way compares every record of one with every record of the other. The result can also be large, and it must often be written back to disk as an intermediate result.

The optimizer's job is to pick, for each operation, an algorithm that fits the available comparison and access structure:

1Look at the condition: simple, conjunctive (AND) or disjunctive (OR)?
↓
2Look at the comparison: equality or non-equality?
↓
3Look at the access path: none, ordered file, or an index?
↓
4Pick the algorithm whose estimated block count is smallest
No dumb questions
Is "optimizer" the same as "the best plan"?
No. It looks for a reasonably good plan using estimates. The slide lists four ways of saying the same goal, and the last one is the practical one: fewest block reads, because disk access dominates everything else.
Why do the slides count blocks and not records?
The disk delivers a whole block at a time. Reading one record or ten records in the same block costs the same single block read.
Brain powerThe query SELECT * FROM EMPLOYEE contains only a projection. Why is it never described as "a bottleneck" the way a join is?
Lesson 02

Aggregate operators: MAX, MIN, SUM, AVG, COUNT

Aggregates turn a set of rows into one number. With the right structure they can be astonishingly cheap.

From the lectureAggregate operators: functions that operate on sets (COUNT, SUM, AVG, MAX, MIN). They produce numbers (not tables). You needn't the whole row.
Example: SELECT MAX(Salary) FROM EMPLOYEE;

An aggregate collapses many rows into one number. The key observation from the lecture is in the last bullet: you do not need the whole row, only one column. That lets the DBMS read less, and a good index can answer the question without touching the table at all.

Three situations

SituationWhat the DBMS doesCost idea
An index exists on the columnIndex scan: walk the index instead of the tableA few index blocks (tree height) for MIN/MAX; the whole leaf level for SUM/AVG
No index, table sorted on the columnThe min and max are readily available: first and last recordAbout one block read
No index, table not sortedTable scan: read every block, keep a running answerb blocks (the whole file)

Aggregates on a B⁺-tree index

AggregateHow an index answers itWhy
MAXTraverse until the right-most index keyKeys are ordered; the largest is at the far right
MINTraverse until the left-most index keyThe smallest is at the far left

AVERAGEVisit all keysNeeds the sum and the count, so every value again

ExampleWhich is cheapest? For a table of 2,000 blocks: MAX with an index on Salary reads about the height of the index (say 3–4 blocks). MAX on a sorted file without an index reads the last block (1). MAX on an unsorted file with no index reads all 2,000. SUM(Salary) needs every salary in all three cases; the index only helps by letting the DBMS read the narrow index leaf level instead of the wide table rows.
Watch it!MIN/MAX are not like SUM/AVG. MIN and MAX need just one end of the ordered structure; SUM and AVG need everything. Only COUNT (of the whole table) can be free, because the catalog already stores it. A COUNT with a WHERE condition is a different story: the catalog cannot know it.

Lesson 03

GROUP BY: sort, partition, aggregate

Grouping means finding all the rows that share a value. Sorting is the standard way to bring them together.

From the lectureGROUP BY: SELECT Dno, AVG(Salary) FROM EMPLOYEE GROUP BY Dno;
Sorting approach: (1) sort the relation on the grouping attributes; (2) partition the relation into groups by the grouping attributes; (3) apply the aggregate operators on the groups.
Computation is complex. Clustering index → already grouped.

GROUP BY is an aggregate repeated once per group. The difficulty is finding the groups: employees of department 3 are scattered through the file. The lecture's solution is the same trick that solves many full-relation problems: sort so that equal values become neighbours.

Why the clustering index is a gift

A clustering index on Dno means the file is physically ordered by Dno. The data is already grouped, so step 1 (the expensive sort) disappears: the DBMS just reads the file once and cuts a group every time Dno changes. Without it, sorting costs far more than the single pass that follows.

No dumb questions
Why is it called "complex computation"?
Because step 1 is a full sort of the relation, which itself takes several passes over the data when the relation is bigger than memory.
Can I group by two attributes?
Yes. Sort on the pair (first attribute, then second). Equal pairs become neighbours, and so do the groups.
Brain powerTen employees, three departments. After sorting by Dno, how does the algorithm know where one group ends and the next begins? Which single comparison does it need between neighbouring records?
Lesson 04

The optimizer's vocabulary: conditions, comparisons, access paths, selectivity

Three questions the optimizer asks about every operation, plus the one number it needs to predict output size.

From the lectureAlgorithms — the three dimensions the optimizer looks at:
Conditions: simple (one comparison), conjunctive (multiple comparisons with AND), disjunctive (multiple comparisons with OR).
Comparisons: equality, non-equality.
Access paths: none, ordered file, index.
DimensionOptionsExample
Conditionsimple / conjunctive (AND) / disjunctive (OR)Dno=5 · Dno=5 AND Salary>300 · Dno=5 OR Dno=7
Comparisonequality / non-equalityDno = 5 · Dno > 5
Access pathnone / ordered file / indexheap file · file sorted on Dno · index on Dno

Condition selectivity (sl)

From the lectureCondition selectivity (sl) is the percentage of the records that satisfy the condition, a number in [0, 1].
Equality condition on a key attribute (e.g. Name = 'Allen, Sam'): selectivity = 1 / relation size.
Equality condition on a non-key attribute with i distinct values that are uniformly distributed (e.g. Dept_number = 1): selectivity = 1 / i.
s = sl × rselection cardinality: the average number of records that satisfy the condition (r = number of records)
ExampleEMPLOYEE has r = 10,000 records.
  • Ssn = '1234': key, so sl = 1/10,000 = 0.0001 and s = 1 record.
  • Dno = 5: 125 distinct departments, uniform, so sl = 1/125 = 0.008 and s = 10,000 × 0.008 = 80 records.
  • Gender = 'F': 2 distinct values, so sl = 0.5 and s = 5,000 records. Half the table is not "selective" at all!
Watch it!Uniform distribution is an assumption. If one department secretly holds half of all employees, 1/i underestimates Dno = that department badly. This is why real systems also keep histograms (see the heuristics and cost-based guide).
No dumb questions
Small sl or large sl: which is "more selective"?
A small sl is more selective (few records pass). sl = 0.0001 is excellent; sl = 0.5 is poor.
Why does join algorithm choice need selectivity at all?
Because it predicts how many records match: the size of the output and how many index probes return many records.
Lesson 05

Join basics: scope and the three methods

The lecture restricts itself to the case that matters most in practice: equi-joins between two files.

From the lecture⋈ Algorithms — scope: only equi-join (i.e. no theta-join); only two-way join (i.e. no multi-way join), e.g. R ⋈A=B S, not R ⋈A=B S ⋈C=D T.
Examples: EMPLOYEE ⋈DNO=DNUMBER DEPARTMENT and DEPARTMENT ⋈MGRSSN=SSN EMPLOYEE.

An equi-join keeps the pairs (r, s) where r[A] = s[B]. Anything other than "=" (a theta-join such as A < B) is outside the lecture. A two-way join joins exactly two files. A three-table query R ⋈ S ⋈ T is executed as a sequence of two-way joins: first R ⋈ S (stored as an intermediate result RS), then RS ⋈ T.

The three methods

From the lectureMethods for implementing joins: Sort-merge join [both files are ordered on the join attribute]; Single-loop join [using an index to retrieve the matching records]; Nested-loop join [linear search].

Sort-merge

When: both files ordered on the join attributes.
How: walk both files once in parallel, matching as you go.
Cost: the cheapest by far.

Single-loop

When: one relation has an index on its join attribute.
How: for each record of R, probe the index on S.
Cost: one loop instead of two.

Nested-loop

When: no index on either join attribute. The fallback, always available.
How: read a chunk of R into memory, scan all of S against it, repeat.
Cost: the most expensive.
Watch it!Numbering trap. The labels J1/J2/J3 are not consistent across your slides. In the Week 4 slides the overview page lists sort-merge as J1, single-loop as J2 and nested-loop as J3, but the detailed slides title nested-loop (J1), single-loop (J2) and sort-merge (J3), and the Week 6 cost slides use the same J1/J2/J3 = nested/single/sort-merge. This guide follows the detailed slides and Week 6: J1 nested-loop · J2 single-loop · J3 sort-merge. In an exam, always write the name next to the label.

Choosing among them

?Are both files already ordered on their join attributes?
yes → sort-merge (J3), cost bR + bS (+ output)    |    no ↓
?Does one relation have an index on its join attribute?
yes → single-loop (J2), probe that index    |    no ↓
!Nested-loop (J1): always works
Watch it!This is a first filter, not the final answer. The decision flow tells you what is possible. The optimizer still computes the cost of every possible plan, and an indexed single-loop join can lose to a nested-loop join when the outer relation is big and the buffers plentiful (you will see exactly this in Lesson 11).
Lesson 06

How big is a join result? Join selectivity

Before costing a join we need to know how many blocks of output it writes.

Join cost has two parts: the cost of reading the input files, and the cost of writing the result. The second part needs an estimate of how big the result is.

Why the result size matters

From the lectureWhat is the problem about join? The result should be stored, and other operations may be done on it ("intermediate results"). The resulting file is stored to disk. R ⋈ S ⋈ T ≡ (R ⋈ S) → store result as RS, then RS ⋈ T. How to estimate the result?

Join selectivity (js)

js = |R ⋈A=B S| / |R × S|0 ≤ js ≤ 1 · the fraction of the Cartesian product that survives the join condition

No join condition

That is a Cartesian product: every pair survives, so js = 1.

No matching tuples

Nothing survives, so js = 0.

From js to blocks

result records = js × |R| × |S|
result blocks = ⌈ (js × |R| × |S|) / bfrRS ⌉bfrRS = blocking factor of the result file (records per block)
ExampleEMPLOYEE ⋈Dno=Dnumber DEPARTMENT. |EMPLOYEE| = 10,000, |DEPARTMENT| = 125, js = 1/125, bfrED = 4.
result records = (1/125) × 10,000 × 125 = 10,000. That makes sense: every employee belongs to exactly one department, so the result has one record per employee.
result blocks = 10,000 / 4 = 2,500.
No dumb questions
Where does js = 1/125 come from?
DEPARTMENT's join attribute (Dnumber) is a key with 125 values, and every EMPLOYEE record matches exactly one. In a key–foreign key join, js = 1 / |relation holding the key|.
Is the result blocking factor the same as the inputs'?
No. Result records are wider (they carry the attributes of both), so fewer fit per block. That is why bfrED = 4 here while EMPLOYEE has bfr = 5 and DEPARTMENT has bfr = 10.
Key pointEvery join algorithm pays the same output term, (js × |R| × |S|) / bfrRS. It does not depend on the algorithm. Only the reading part differs, which is why the lecture compares algorithms on their reading cost.
Lesson 07

Nested-loop join (J1)

The fallback that always works: compare everything with everything, but block by block.

From the lectureNested-loop join (J1), aka nested-block join. When: no indexes are available for the joining attributes. How: for each block in R (outer loop), for each block in S (inner loop): compare each record in R's block with each record in S's block; if r[A] == s[B] add r[A]+s[B] to the result set.
for each block br in R:             -- OUTER loop
    for each block bs in S:         -- INNER loop
        for each record r in br, s in bs:
            if r[A] == s[B]:  add r + s to the result

Join on R.C = S.C. The algorithm compares every R record with every S record (4 × 4 = 16 comparisons) and finds three matches:

Two ideas to hold on to

Outer relation

Read once, a chunk at a time. Its blocks are read exactly bR times in total.

Inner relation

Read again and again: once per chunk of the outer relation. This is the term that hurts.
From the lectureFactors affecting JOIN performance: available buffer space [memory buffers] and the choice of inner vs outer relation.
Brain powerIf R has 1 block and S has 1,000,000 blocks, how many times is S read when R is the outer relation? And if S is the outer relation and R the inner?
Lesson 08

Buffers and the choice of outer relation

The same join can cost 19 blocks or 17 blocks depending on which file you put outside. Here is why.

The lecture poses a question on two successive slides: "Which is better, R ⋈A=B S or S ⋈B=A R? Calculate the number of blocks that are read. It depends on who is the smaller and bigger relation." Same join, same answer, different cost, just by swapping which file is outer.

Counting block reads

Take R with bR = 7 blocks, S with bS = 3 blocks. The buffer lets us hold 2 blocks of the outer relation at a time.

bR + ⌈ bR / Buffers ⌉ × bSR in the outer loop · "Buffers" = how many outer blocks fit in memory at a time
Outer relationFormulaChunksTotal reads
R (7 blocks)bR + ⌈bR/2⌉ × bS = 7 + 4 × 3419
S (3 blocks)bS + ⌈bS/2⌉ × bR = 3 + 2 × 7217
The ruleRule: put the SMALLER relation in the outer loop. The outer relation is read once either way (7 or 3); what changes is the number of chunks, and each chunk costs one full scan of the inner relation. Fewer blocks outside → fewer chunks → fewer scans of the big file.

From "Buffers" to nB − 2

From the lectureAssume the memory buffer is nB blocks: cost = bR + ⌈bR/(nB − 2)⌉ × bS + (js × |R| × |S|)/bfrRS — "Why?"

The slide leaves the why as a question. Here is the answer. Of the nB memory blocks you cannot give all of them to the outer relation:

  • 1 block to read the current block of the inner relation S;
  • 1 block as the output buffer where result records are built before being written;
  • the remaining nB − 2 blocks hold the outer chunk.

So in the first example, "we consider 2 blocks to read from outer R" means nB − 2 = 2 (nB = 4). That is why the quiz question "bR = 7, bS = 3, nB = 4" has the answer 19.

How much do buffers matter?

EMPLOYEE (b = 2,000) joined with DEPARTMENT (b = 13), DEPARTMENT outer, plus the 2,500 output blocks:

nBChunk (nB−2)Chunks ⌈13/chunk⌉Reading cost 13 + chunks × 2000Plus output 2,500
311326,01328,513

Watch it!Once the outer relation fits entirely in memory, more buffers help no more. At nB = 15 the whole of DEPARTMENT (13 blocks) sits in memory and EMPLOYEE is read just once. With nB = 100 the cost is still 4,513.
No dumb questions
Why not just give the inner relation more buffers?
It does not help: the inner relation is scanned sequentially, one block at a time, and each block is used immediately. Buffers pay off only for the outer relation, because a bigger chunk means fewer scans of the inner one.
Is the output term affected by the swap?
No. Both orders produce the same result records, so the output cost is identical. Only the reading cost depends on which relation is outer.
Lesson 09

Single-loop join (J2)

Replace the inner loop by an index lookup. One loop, many probes.

From the lectureSingle-loop join (J2). When: one table has an index on its join attribute. How: assume table S has an index on attribute B. For each block b in R, for each record r in b: retrieve the record in S with B = A using the index.
for each block b in R:                       -- one loop over R's blocks
    for each record r in b:
        use the index on S.B to fetch the records with B = r[A]
        add each (r, s) pair to the result

For each Dept record, the DBMS asks the index "where are the students with DeptNum = this DeptID?" and jumps straight to those data blocks. IT (1) finds nothing; IS (2) finds two blocks' worth; OR (3) one; CS (4) two. Students of other departments are never read. That is the whole advantage: S is not scanned, only probed.

The cost formulas

From the lecturePrimary index: bR + (|R| × (xB + 1)) + (js × |R| × |S| / bfrRS)
Clustering index: bR + (|R| × (xB + ⌈sB/bfrB⌉)) + (js × |R| × |S| / bfrRS)
Secondary index: bR + (|R| × (xB + 1 + sB)) + (js × |R| × |S| / bfrRS)
SymbolMeaning
bRblocks of the outer relation R (read once, sequentially)

Why these three shapes?

The part in the middle is the cost of one probe, times |R| probes:

Index on S.BOne probe costsReason
PrimaryxB + 1x index blocks to find the key, then 1 data block (one match, key is unique)
ClusteringxB + ⌈sB/bfrB⌉x index blocks, then the matching records are contiguous, so they occupy only ⌈s/bfr⌉ blocks
Secondary (non-key)xB + 1 + sBx index levels, 1 pointer block, then each of the s matches may sit in a different data block
Watch it!|R|, not bR. The outer file is read block by block (bR reads), but the index must be probed once per record, because each record carries its own join value. A block of 5 employees needs 5 probes, not 1.
No dumb questions
Which relation should be outer in a single-loop join?
The one without the useful index is the outer one (it gets read sequentially); the indexed relation is probed. If both have indexes, try both and pick the cheaper: usually the one with fewer records as outer, since |R| multiplies the probe cost.
Why is a clustering-index probe cheaper than a secondary one?
Matching records sit next to each other, so s matches need only ⌈s/bfr⌉ blocks instead of up to s blocks.
Lesson 10

Sort-merge join (J3)

Two sorted files, two pointers, one pass: the cheapest join there is, if the files are already ordered.

From the lectureSort-merge join (J3). When: R is ordered by A and S is ordered by B. Cost: bR + bS + ((js × |R| × |S|) / bfrRS).

If both files are sorted on their join attributes, matching records are neighbours in both files, so two pointers walking down the files once will meet every match. Each file is read exactly once.

The algorithm

sort the tuples in R on attribute A;   -- skip if already sorted
sort the tuples in S on attribute B;
i ← 1; j ← 1;                          -- n = |R|, m = |S|
while (i ≤ n) and (j ≤ m) do {
  if      R(i)[A] > S(j)[B]  then j ← j + 1
  else if R(i)[A] < S(j)[B]  then i ← i + 1
  else {                                   -- R(i)[A] = S(j)[B]: a match
     output <R(i), S(j)> to T;
     l ← j + 1;                           -- other S tuples matching R(i)
     while (l ≤ m) and (R(i)[A] = S(l)[B]) { output <R(i), S(l)> to T; l ← l + 1 }
     k ← i + 1;                           -- other R tuples matching S(j)
     while (k ≤ n) and (R(k)[A] = S(j)[B]) { output <R(k), S(j)> to T; k ← k + 1 }
     i ← k; j ← l                         -- jump past the whole group
  }
}

cost = bR + bS + (js × |R| × |S|)/bfrRSreading each file once + writing the output
ExampleEMPLOYEE (2,000 blocks) ⋈ DEPARTMENT (13 blocks), both already sorted on the join attributes: 2,000 + 13 + 2,500 = 4,513 blocks. Compare that with the nested-loop plan with only 3 buffers: 28,513.
Watch it!"Already sorted" is a big assumption. The formula bR + bS does not include sorting. If a file is not sorted on the join attribute, the cost of sorting it must be added, and sort-merge may then lose to a single-loop or nested-loop join. When the file is sorted (for example by a primary or clustering index on that attribute), sort-merge is the cheapest of the three.
Watch it!Duplicates on both sides. The pseudocode above pairs R(i) with the whole run of equal S records (pointer l) and S(j) with the whole run of equal R records (pointer k). That covers the case drawn in the lecture, where only one side has duplicates (two or three Students per Dept). If both files contain a run of equal values, the true join must output every pair of the two runs (2 × 3 = 6 pairs for runs of 2 and 3), so a complete implementation loops over both runs. In an exam, say "all matching pairs".
No dumb questions
What is the point of k and l?
Duplicates. Pointer l walks the run of equal join values in S for the current R record; pointer k walks the run in R for the current S record. They let the merge cope with repeated join values instead of assuming each value occurs once.
Does sort-merge work for non-equality conditions?
Not in this lecture: only equi-joins are covered.

Key ideas

  • Aggregates: MIN/MAX follow one tree edge, SUM/AVG visit all keys, COUNT is in the catalog.
  • GROUP BY: sort, partition, aggregate; a clustering index skips the sort.
  • Selectivity: 1/|R| for a key, 1/i for a uniform non-key; s = sl × r.
  • Join size: js × |R| × |S| records, divided by bfrRS for blocks.
  • Nested-loop: smaller relation outer; buffers nB − 2 for the chunk.
  • Single-loop: |R| probes; formula depends on the index type.
  • Sort-merge: bR + bS if already sorted.

Part C · Written (model answers)

46MAX follows the right-most key; MIN the left-most; both cost only the tree height because keys are ordered. SUM and AVG must add every value, so they visit all keys (the whole leaf level); there is no shortcut. COUNT is usually a catalog statistic and is found directly. So MIN/MAX are cheap because they need one end of an ordered structure, SUM/AVG need all of it.
47(1) Sort the relation on the grouping attributes, so equal values are adjacent; (2) partition the sorted relation into groups, cutting whenever the grouping value changes; (3) apply the aggregate (AVG, SUM…) to each group in the same pass. The sort is the expensive step. With a clustering index on the grouping attribute the file is already ordered by it, so the data is already grouped and the sort is skipped: one pass suffices.
48The outer relation is read once: bR blocks. Of nB buffers, one holds the current inner block and one is the output buffer, leaving nB − 2 for the outer chunk, so there are ⌈bR/(nB−2)⌉ chunks. Each chunk requires a full scan of S (bS blocks). Total = bR + ⌈bR/(nB−2)⌉ × bS. The outer relation is read once whichever it is; the number of chunks, which multiplies the inner scan, is smaller when the outer relation is small. Example: 7 + 4×3 = 19 versus 3 + 2×7 = 17.
49When R(i)[A] = S(j)[B] a match is output. Pointer l looks ahead in S from j + 1 and outputs R(i) with every following S record having the same value. Pointer k looks ahead in R from i + 1 and outputs every following R record with that value paired with S(j). After the group, i is set to k and j to l so both files jump past the run of equal values, and every record is visited essentially once. (If both files hold runs of equal values, a complete join must output all pairs of the two runs.)
50The cost is dominated by |R| × (probe cost). With EMPLOYEE outer there are 10,000 probes at x + 1 = 2 blocks each: 20,000. With DEPARTMENT outer there are only 125 probes, each costing x + 1 + s = 83 blocks through the non-key secondary index on Dno: 10,375. Fewer outer records beats cheaper probes. Totals: 24,500 versus about 12,888.
